## 2. 合并动作与版本

可 fast-forward（落后 0，领先 2）：把 `feat/plugin-surface` 快进合并进 main，无冲突、无 merge commit 必要。tag 建议命名 `v1.2.0`。

版本结论：**建议 bump 到 1.2.0**。理由链条：上一轮已修复"同一版本号对应两份不同内容"的隐患（`mavis版本bump方案_确证_20260918.md`），当前 `1.1.0` 这个号对应的内容是"含三个注入钩子（`external_state` / `interaction_request` / `role_directive`）及 `transfer` 配置、不含插件面"。（注：mavis 里没有名为 `scope` 的钩子，`scope` 只是 `agent_core.py:790` 的局部变量与 `scene/maze.py:178` 的 `get_scope()` 方法，与注入面无关。）若插件面合入后保持 `1.1.0` 不 bump，就把"含插件面的源码"与"不含插件面的 1.1.0 制品"挂到同一个版本号下，恰好重新制造那个隐患：dist/制品与源码内容不一致，复现环境按版本号装会拿到不含插件面的老内容。因此 bump 是消除隐患的必要动作，不是锦上添花。bump 到 1.2.0（次版本）符合语义：新增能力、默认关闭、API 表面向后兼容，不应算补丁级 1.1.1（那是 bugfix），也不该跳到主版本 2.0（没有破坏性变更）。

被否选项与理由：不 bump（若依赖走 Git 直接 pin commit，则版本号不参与分发，但本地 editable 与后续 wheel 产物仍会形成同号冲突，隐患依旧）；bump 到 1.1.1（语义不符，插件面是新增能力而不是修 bug）；bump 到 2.0.0（过重，无破坏性变更，会给所有使用者带来无谓的语义升级负担）。

执行顺序（若拍板执行）：先在 main 上把 `feat/plugin-surface` 快进合并；再在 main 上 bump 版本提交并重建制品、解包校验（对齐 bump 方案第 2/3 节）；随后打 tag `v1.2.0`；最后 provenance 更新 pin 到含插件面的版本。

## 3. 合并后的基线锚点

provenance 的 CI 从 mavis main 装框架。合并后建议在 CI 增加一条前置断言：装完框架后在隔离目录 import 并探测 `mavisframework.plugin`、`agent_core.subscribe_chat_line`、`Simulator` 签名含 `plugins=` 三要件齐全后才继续，否则 CI 先红（防止容器错装到不含插件面的老制品仍"通过"）。阶段 3 新包用 commit hash 或 `v1.2.0` tag 固定基线：requirements 里对新包写死 `mavisframework @ git+<repo>@v1.2.0`（或对应 hash），使抽包实现始终针对"已合进 main 的公开 API"，不再跟随分支移动。

## 4. 回滚方式

三种并存：revert 合并提交或 bump 提交（保留分支历史，最干净）；重置到前一 tag（回 `v1.1.0` 基线，但会丢合并后提交，不宜共享分支用）；保留 `feat/plugin-surface` 分支不删（随时可重新合）。回滚对已依赖插件面的代码的影响：插件面默认关闭、特性探测存在回退路径，回滚到不含插件面的 main 后，case01 的 `VizForwarder` 探测不到插件面自动走回退路径（`on_story` + 全局 `chat_callback`），功能不中断、只降级接线方式，无需改 case01 代码。唯一注意：若已发布的制品与回滚后 main 源码版本号不一致，需随回滚同步 rebuild，避免再次同号错配。
