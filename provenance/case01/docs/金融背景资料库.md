# case01 前置金融背景资料库

> **状态**:现行
> **最后核对**:2026-10-08
> **说明**:100 条外部公司资料的导入、可选检索、分段和审计方式。

## 定位与启用

这批资料在 case01 咨询开始前已存在，供 Investment AI 查询。导入不会自动产生
角色经历、初始记忆或 LoRA 训练样本。文件标注的日期为 2025-02-20 至 2026-08-24，
早于 case01 T0（2026-08-27）；尚未独立核验原始来源。

默认保留原有 HCM 资料检索。启动新运行前，设环境变量启用背景库：

```bash
# 从仓库根启动普通 case01（使用已装好依赖的 Python）
CASE01_FINANCIAL_BACKGROUND=1 python provenance/case01/run.py --run-id background-demo

# 小镇路径同样读取此环境变量，例如启动全部服务并实际运行
CASE01_FINANCIAL_BACKGROUND=1 python tools/serve_all.py --full
```

PowerShell 用 `$env:CASE01_FINANCIAL_BACKGROUND="1"`，然后执行原有启动命令。
设置为 `0` 或取消环境变量，恢复原有资料检索方式。已运行进程不会自动切换，需要在
下一次新启动时启用。批量运行的子进程继承环境变量。

## 文件位置与重新生成

- `case01/data/financial_sources/模型版_100条.jsonl`：原始文件，逐字节保留。
- `case01/data/financial/background/<股票代码>/docs.json`：10 家公司的 100 条标准化全文。
- `case01/data/financial/hcm/docs.json`：原有 HCM 案例资料，保持原文。
- `case01/tools/import_financial_background.py`：无网络、无 LLM 的确定性转换工具。

仓库根的重复原文件已删除，导入工具默认读取上述已入库的原始文件。重新生成可执行：

```bash
python provenance/case01/tools/import_financial_background.py
```

转换保留中文公司名称、股票代码、来源、类型、正文和原始时间字段；增加文档 ID、
原文件行号和 SHA-256。原文没有 URL，不补造 URL；不把资料类型推断成可信度或独立来源。
存在报告日期/官网日期或两个冲突日期时，采用字段中的较晚日期作为可见日，原始字段
仍保留。日期只有日精度，不宣称支持同日内发布时间隔离。格式无法解析会报错。

## 分段与检索

启用背景库时，加载后将全文构建成不超过 600 字符的片段。优先沿自然段分界，
段落过长则沿句号等句子边界分割；单句超过上限才硬切。所有片段合起来与原文一致，
每段保存原文 ID、片段 ID 和 `[char_start, char_end)` 字符位置。

普通 case01 在用户每轮提问时检索：

1. 目标公司资料（`background/` 之外那批，当前就是 HCM）保留最多 8 个文档名额，每篇取最相关片段。
2. 额外补最多 2 篇背景资料的相关片段，标注公司、标题和“市场背景资料”。
3. 两类结果均限制发布时间不晚于当前模拟日；同一篇文章不会重复占名额。
4. 模型收到完整命中片段，而非命中文章的开头 600 字。

这是为当前 HCM 场景保留证据名额的检索策略，并非自动识别任意目标公司的路由器。
主料名额只按“背景 / 非背景”分，**不在代码里写死公司名**（2026-10-08 改）：此前
`search_context` 带 `company="hcm"`，接第二家目标公司时它的资料会**静默进不了主料池**；
同库对照实测旧写法主料池 8 条全为 hcm、新写法为 hcm 8 + 第二家 3，背景库仍不混进来。
默认关闭时仍使用原有全文排序/开头 600 字逻辑，因此新旧实验应分组比较。

小镇路径原有资料来自节点事件注入。启用背景库后，在咨询节点按节点的 `focus`
检索最多 2 篇背景资料，只放入 Investment AI 的临时上下文，不提前塞进 Ethan 的
记忆；原有事件注入保持原样。它不是按每一句实时对话重新检索，记录用
`query_source=node_focus` 明确区分。检索有可用 embedding 时使用向量排序，否则使用
原有关键词降级；中文整句的关键词降级能力有限。首次向量检索需要计算片段向量，
后续在同一实例内按完整文本缓存。

**首检索的实测规模**（2026-10-08，本机离线构造 `FinancialData`，用一个计数桩替掉
真实 embed，不调 LLM）：入库的 120 份文档切成 **386 个片段**，一次首检索发出
**385 次串行 embed 请求**（片段文本相同的命中缓存只算一次），同一实例内第二次检索为
**0 次**。⇒ 开这个开关的代价落在**每个进程的第一个咨询节点**上：重启实时面或另起一批都会
重来一次；演示日若临时启用，先按"第一个节点要等几百次串行请求"预估。

## 审计

`retrievals` 的每次记录包含：

- `library`：开关、实际加载资料的内容哈希、文档/片段数、分段版本及排序方式、
  `embed_backend`（向量是谁给的：判官客户端 / 环境变量新建的本地客户端 / 无=关键词降级，含模型与地址）、
  `skipped_json`（资料目录里读不出或不是数组、因此**没被当资料**的文件名）。
- `hits`：原文/片段 ID、来源、时间、公司、原文位置、实际提供的正文片段及原文件哈希。
- `context`：拼装给模型的资料上下文。

`meta.source_sha256` 是**换行归一后**的语料字节哈希（`import_financial_background.source_fingerprint`）：
仓里没有 `.gitattributes`，同一份 JSONL 在 Windows 检出后每行多一个 `\r`，直接按文件字节哈希会随
检出机器的换行配置变化，而这条指纹是用来声明"100 条来自同一份语料"的证据，所以按 LF 归一后取。

小镇原始节点记录保留 `background_retrievals`，映射成成品记录后单独作为
`mode=background_retrieval` 的检索行，和 `mode=injection` 的事件材料区分。
`manifest.financial_data_version` 仍是磁盘整个资料目录的哈希；本次启用资料的版本
以 `retrievals[].library.corpus_version` 为准。同一文档的多个片段只算一次来源记录。

本次接入不意味着已用真实 LLM 完成新实验，也不改变历史样本的证据和结论。
