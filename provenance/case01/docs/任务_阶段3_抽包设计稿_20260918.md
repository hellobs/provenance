## 0. 抽包前的耦合事实(不改现状的观测)

先列清楚 injector 与外部的大多数依赖边,作为下面取舍的依据。以下是本机实读
`Select-String` 得到的 import 边,不含臆测。

injector → case01 其它模块:

- `nodes.py` → `..world.timelines`
- `worldfacts.py` → `..world.state`、`..world.timelines`、`..world.branch`、`..orchestrator`
- `bridge.py` → `.worldfacts`、`..world.branch`、`..agents.llm`
- `pipeline.py` → `..agents.llm`、`..reflection`、`.worldfacts`
- `record.py` → `..world.timelines`

bridge 对 mavis 框架与 mavis-vizkit 的依赖是**无条件 import**(见 `_build_mavis`:
`mavisframework.config.loader.load_config`、`mavisframework.core.timer.Timer`、
`mavisframework.runtime.game.Game`、`mavisframework.runtime.simulator.Simulator`,
以及 `mavis_vizkit` 的 `Fanout` / `create` / `events`);只有 `mavisframework.plugin`
是特性探测的特例。这条边决定 §1 的外部依赖写法:bridge 随包后,新包对
mavisframework 与 mavis-vizkit 是**硬依赖,不是可选**。

world 侧:完全纯净,只 import 标准库(`typing` / `dataclasses` / `json` / `os` / `re`),
没有任何指向 case01 其它模块的边。

injector 的入向使用者(现状):`case01/tests/*`、`case01/tools/isolation_probe.py`、
`case01/vizkit/live_run.py`。

因此:抽包的本质是把 injector 连同它依赖的 `world/`(以及它实需的几位"辅助"——
LLM 客户端与反射路由的窄接口)一起拿走,同时保证上面这些入向使用者的导入路径
不破碎。world 因为纯净,是无痛的随迁对象;真正的取舍集中在"world 怎么带""辅助
放谁侧""反向依赖怎么处理"三件事上。

## 1. `case01/world/`(timelines / branch / state)与 injector 强耦合,怎么处理

结论:把 `world/` 作为新包的内部子包一并迁入,不打散、不另起 `case01-core` 包。
新包对外名 `mavis_case01_injector`,内部含 `world`、`nodes`、`bridge`、`pipeline`、
`record`、`worldfacts`、`conditions`、`viz_plugin` 等模块;`agents.llm` 与
`reflection` 只收编 injector 运行实需的窄子集。

理由:world 与节点生成、bridge 的注入是构造期强依赖(nodes 在构造 bridge 前就要
从 timelines 算出节点序列),它不是"可运行期临时注入的数据",而是模块的组成部分。
world 自身纯净、无 mavis 依赖、无指向 provenance 的反向依赖,把它原样搬到包内
零成本,做不做成"独立的 case01-core 包"没有第二消费者支撑,多一个包只多一份发布
与版本负担。把这两个窄辅助(一个薄 LLM 客户端、一个反射路由入口)以"可替换
provider"的形态收进包内,使包除 mavisframework 与 mavis-vizkit(硬依赖,bridge 无条件
import)以及运行期由调用方注入的 scenario 资源根与外部 LLM provider 之外,不再有
其它外部依赖。

被否方案与理由:

- 把 world 做成"由调用方传入的 provider":world 与节点生成是构造期依附,注入只会
  把"谁构造 world"的复杂度上移到每次挂载点,耦合并未消失,只是换了个地址,
  还让"独立可挂载"变成"必须连着一套 world 装配一起给"。否。
- 新包反向依赖 provenance 的 case01:`from provenance.case01.world import ...` 会让
  新包在安装时带上传入方整个 provenance 代码库,直接违背"独立可挂载"目标,并形成
  与 case01 导入环路的风险。否。
- 抽两个包(world 一个、injector 一个,即 `case01-core` + `mavis-case01-injector`):
  world 目前只有 injector 一个消费者,没有第二个消费者来摊薄它的独立版本化成本。
  否(留作后续真有第二个消费者时再拆)。

对"独立可挂载"目标的影响:world 并入后,新包成为自封闭的"注入器 + 世界事实层"单元,其必须的外部依赖是(1) mavisframework 与 mavis-vizkit(硬依赖,bridge 无条件
import,实施时写进新包 pyproject);(2) 运行期由调用方注入的 scenario 资源根与外部
LLM provider;(3) 可选的插件面**路径**(存在则推进,不存在则回退——这是运行时走哪条
路径的可选,不是"是否依赖 mavis 框架"的可选)。这样新包可被
`Simulator(plugins=[...])` 或任何驱动脚本独立挂载,不携带 provenance 的任何本体。

## 2. 依赖方向与顺序:插件面还没合 main,provenance 该依赖哪个 commit,先合还是先抽

结论:顺序为 ① 先把 mavis 插件面合进 main,② 再基于已合的 API 抽包,③ 最后让
provenance 依赖指向"含插件面的 mavis 版本 + 新包版本"。

理由:抽包的目标是让新包与 mavis 的插件面契约一致;契约还没有冻结在 main 上时,
`feat/plugin-surface` 是一条可能再被 review 修订的分支。若先抽包、后合 main,
抽包与合并之间的每一次接口修订都要回改新包,等于把"稳定基线"建立在流沙上。
反过来,先把插件面合 main(git tag 如 `v1.2.0`,或至少确认它来自 main 的
`HEAD`),新包针对"已合进 main 的公开 API"写,后续只跟版本号,不再跟分支移动。

依赖锚点:新包的 pyproject 不写死 mavis commit,而是(1) 运行时用特性探测
(`try: from mavisframework.plugin import Plugin`)保证对 mavis main 也兼容;(2)
测试与 CI 用 `pip install git+https://github.com/.../mavis.git@<插件面已合的 commit
或 tag>` 固定一个"至少含插件面"的基线,把"该基线上有插件面"写进 CI 前置断言。
这样 provenance 的 CI(它从 mavis main 装框架)在插件面合入前靠回退路径,合入后
靠插件面路径,两者都绿;新包不因此阻塞在某个 branch。

被否方案:先抽包再等合 main——新包在接口未冻结期间反复适配,浪费且不必要;且
抽包验收(需跑 mavis 插件面契约测试)会依赖一条未合的 branch,验收结论不可复现。否。

## 3. 抽包后 provenance 侧的共享件怎么办(serve / reflection / full_context / render / viz / vizkit 薄壳)

归属判断标准(先定标准,再逐件套):该模块是否落在 injector 的"运行时依赖闭包"
内,且迁走后能否保持零反向依赖。在闭包内且能保持零反向 → 随包走;否则留在
provenance。

随包走:

- `case01/world/` 全部(state / timelines / branch)。理由见 §1,它们是 injector 的
  运行时依赖且纯净。
- injector 自身:`nodes` / `bridge` / `pipeline` / `record` / `worldfacts` /
  `conditions` / `viz_plugin` / `run_injector`,整体搬家。
- 窄辅助:LLM 客户端**窄子集**(injector 运行闭包内实需的全部客户端——`pipeline` /
  `bridge` 用到的 `OllamaClient`、`OpenRouterClient`,落在闭包内的 `LocalHFClient`
  一并收编;以"注入式 provider"进包)与反射路由的窄入口(injector 实需
  `run_reflection` / `run_router`),
  以"可替换 provider"的形式对外以公开接口暴露,provenance 如需同款逻辑,应改为依赖新包而非反向复制。

留在 provenance:

- `case01/serve.py`(以及它依赖的 `full_context.py`):这是治理平台的只读服务与
  OpenAPI 固定契约(见冻结的 OpenAPI 规格),属于平台侧,不依赖 injector 的注入
  逻辑,留。
- `case01/reflection.py`:反射的完整实现(8 维)供治理专家接口与全链路审计使用,
  是平台的功能面,不是 injector 的必要依赖;injector 只用到它的窄入口。若窄入口
  随包,完整实现仍留 provenance,由 provenance 侧依赖新包来复用窄入口。留。
- `case01/render.py`、`case01/viz.py`:前端渲染与可视化输出,属治理/平台面,留。
- `case01/orchestrator.py`:它是另一条驱动路径(旧实现侧的编排),本身依赖 world
  与 agents 与 reflection。它不反向依赖 injector,且不是 injector 的必要依赖;
  留在 provenance。注意:worldfacts 现引用 `..orchestrator`,抽包时要把这处改为
  引用包内的等价物(见 §4 步骤)或把该调用下移到包内。留。
- `case01/vizkit/` 薄壳(`live_run.py`):它是 provenance 侧的业务别名与前端根,
  依赖新包暴露的 bridge/nodes 公开接口,留在 provenance。它原本就只 import
  injector 的 `bridge` 与 `nodes`,这两个模块随包后,薄壳改为 `from
  mavis_case01_injector import MavisBridge, default_nodes`,命令行不变。

依据(收束成一句):以"injector 的运行依赖闭包 + 零反向依赖"为界,闭包内且能独立成
环的随之走;治理/平台/协议/渲染这种独立功能面留 provenance,需要时通过依赖新包
来复用,而不做双向依赖。

## 5. 风险清单

- 历史 `run.json` / `runs/` 兼容:阶段 3 抽包**不改**记录 schema
  (`schema_version: injector-0.1`)与 `case01/runs_injector`、`case01/runs`、
  `case01/runs_html` 目录布局;`to_case01_record`
  的键映射、`injector` 元数据键名不得变化。风险:抽包过程中手改 record 结构导致
  旧存档不可读。缓解:抽包只搬文件不改逻辑;把"旧 run.json 能回放渲染"列为回归
  用例(用 `mavis-vizkit.replay` 跑一个抽包前快照)。
- 测试里的相对导入与 `sys.path`:现有测试用 `from case01.injector.*`;抽包后原路径
  失效。风险:漏改或改了但 conftest 的 `sys.path` 注入仍指向旧路径,产生"测的是工作
  树而非包"的假绿。缓解:每套测试都要在"无关目录"验证一次 import 指向已安装包
  (见步骤 8),并且不让 `src/` 出现在根 conftest 的路径里。
- CI 路径与安装方式:provenance CI 从 mavis main 装框架,main 在插件面合入前没有
  插件面。风险:写死 `from mavisframework.plugin import Plugin` 会让 CI 红;或 CI
  同时装新旧两条依赖导致版本打架。缓解:保留特性探测 + 回退(已是阶段 2 结论),
  把"含插件面基线"的 mavis commit/tag 用 `.env`/CI 变量固定,并加一条前置断言
  "该基线上的插件面存在"。
- 旧运行方式归档标签 `archive/case01-old-engine` 不受影响:抽包只迁 case01 当前
  injector 与 world,归档在 git tag 上原样保留,不做任何 tag 操作。风险:误在执行
  途中执行 tag/分支切换。缓解:设计稿明确本阶段零 tag 零分支移动,验收只看文件
  与测试。
- `runs_injector/` 自忽略目录行为不变:`case01/injector/scenario/.gitignore` 里的
  `runs_injector/` 忽略项随 scenario 目录留在 provenance(还是随包?)。风险:抽包
  后新包把 scenario 一并带走时,`runs_injector/` 的忽略语义若没同步,会在 git
  status 里冒出一堆输出目录。缓解:明确 scenario 资源根留在 provenance(injector
  把它作为传入的 scenario_dir,不随包),`runs_injector/` 忽略项原地不变;若确有
  scenario 随包需要,则在包内重建同一条忽略规则并断言 `git status` 干净。

## 6. 不改的边界(反作弊承诺)

- 不改依赖方向:不新增反向依赖、不复制 vizkit / framework 的实现。
- 不造假:迁移结论必须由步骤 4/6 的 grep 与测试数字支撑,不做"看起来独立"的声明。
- 记录 schema 冻结;runs 目录行为不变。
- 本设计稿之外不产生任何代码改动(验收时 `git status` 只应有新增的这份文档)。
