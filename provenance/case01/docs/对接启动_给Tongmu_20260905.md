## 3. Platform / HCI 开工路径(5 步,可与 04/05 对照)

1. **建单**:调 `GET /api/runs` 发现 run;对 `has_reflection=True` 的 run 调
   `GET /api/runs/{id}`,按 `router.issues[]` 逐条建 Expert Review Task
   (每条 Task 关联:run_id + 原始 Reflection 文本 + issue 的
   summary/field/risk/routing_reason)。→ 验收:能列出"待审核队列"。
2. **状态机最小闭环**:Task 状态 pending → assigned(2 专家)→
   approved / edited / rejected;Edit 只改该 issue 对应片段,原始
   Reflection 不覆盖。→ 验收:单专家可走完一单。
3. **Full Context**:任务详情页"View Full Context"按钮调
   `GET /api/runs/{id}/full-context`,以自然语言段落展示
   (不暴露 Branch/内部字段——引擎侧已保证)。→ 验收:专家能看完整记录。
4. **冲突处理**:同 issue 同专业 2 人结论互斥 → Disputed → 追加 3 位
   未参与专家(共 5)→ 多数结论 + 少数意见保留。→ 验收:触发一次冲突走完。
5. **追溯与归池**:关键节点(生成/路由/分配/审核/冲突/结论)记录时间 +
   责任人 + 动作 + 结果,可按 run/reflection 回溯;最终结论可标记
   "进入训练材料池"。→ 验收:一条 run 的完整治理链可查询。

HCI 展示细节见 05 文档与《Governance平台对接说明.md》第 4 节。

## 4. 平台侧待确认问题(引擎侧据此微调,不阻塞先行)

1. **issue 唯一标识**:平台自建 Task 时用 `issue.id`(issue-1..N)+ run_id
   复合主键,还是平台自增 ID 即可?
2. **专家池来源**:首轮 2 人/追加 3 人从"当前可用专家池"动态/随机取——
   专家账号体系用平台现有用户,还是先做 mock 名单?
3. **Edit 的存储**:edited 片段与原始片段并存(建议 same-table 两列或
   关联表);字段命名有无平台约定?
4. **Reflection 文本定位**:问题详情页要显示"与该问题相关的 Reflection
   片段"——引擎目前只给全文;需要按 issue 定位片段,还是要平台端
   自行按 Router 摘要就近截取?(可让 Router 后续输出引用行号)
5. **归池触发**:训练材料池是否在"该 run 全部 Task 达到最终结论"后
   自动聚合?(引擎侧 run.json 已含 experience/reflection/router/audit,
   平台只需存审核结论并外键关联)
6. **数据同步**:新 run 出现的方式定为"平台轮询 /api/runs",无推送事件;
   是否可以接受,还是要引擎加 Webhook?
