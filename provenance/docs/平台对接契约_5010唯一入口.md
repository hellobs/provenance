## 一、一句话

平台只需要**一个地址**:

```
http://<host>:5010/
```

平台**只读**拉取 + iframe 嵌入,不写我们的库;评审流程(建单、专家池、冲突、归池)全在平台侧。
Provenance 不感知平台的存在(`live_switch.py` 起停,平台只负责引地址)。

### 3.1 质检口径(2026-09-21 新增,必须知道)

索引里每条 case01 成品带的质检字段(`live/history.py:271` 的 `_quality_of()` 返回**十栏**:
`quality`/`consistency`/`reason`/`branch_source`/`debug`/`deprecated`/`deprecated_reason`/
`manifest_status`/`manifest_warning_count`/`manifest_warnings`;2026-10-09 订正 —— 此处此前写
"共七项",既没数到 `deprecated` 两栏也没数到警告三栏。**按键的存在性读,别按总数读**):

- `quality`:`ok` / `questionable` / `debug` / `deprecated` / `unverified` / `unreadable`
  **(2026-10-09 订正:本文件此前只列了五值,漏了 `unreadable` —— 而 §3.1 的默认排除集
  `_HIDDEN_QUALITY` 里有它,平台照本句写就认不出那一类)**
  - `deprecated` = **记录被显式标废弃**(如"标 A 的原文实为 B 判据")。**它优先于其它判断**:
    一条自洽的废弃样本同样是废的(2026-09-24 起;此前它只要恰好判成 `ok` 就会被静默发出);
    索引行里同时给 `deprecated: true` 与 `deprecated_reason`,平台要自己筛也有依据;
  - `questionable` = 预设分支与 Investment AI 的 T0 立场自相矛盾(例:AI 说"不能确认值得买"、当事人却满仓),
    或**判定失败**(judge 三次都判不出 A/B/C → run 停在 T0、没有时间线,2026-09-23 起归入这一类:
    这种记录建不出有意义的专家任务,给平台等于让一条废记录去建单);
  - `debug` = 调试跑(如 `--nodes` 截断,内容不完整);
  - `unverified` = 旧记录没有一致性戳 / case00 痕迹 / 压缩成品(**判不了 ≠ 有问题**,照常返回);
  - `unreadable` = **有 run 目录但没有 `run.json`**(该次 run 压根没落盘,`live/history.py:251`)。
    默认不给平台建单,但计入 `excluded`;这一类和下面"哪些行不带 `manifest_*`"是同一条边界。
- `consistency`:T0 立场与分支的一致性判定(`consistent` / `inconsistent` / `unknown` / `unverified`);
- `branch_source`:`preset`(运行参数指定) / `judge`(由 T0 回答判定) / `judge-failed`(判定失败、停在 T0)。
  **口径说明**:受控实验目前默认走 `judge`(即分支由受判主体在 T0 的回答判定),`preset` 保留为对照条件 —— **该默认口径仍待研究侧确认**,确认前请以字段实际取值理解数据;
- `debug`:调试跑说明(空串 = 正式跑);
- `reason`:上面那套判定的**原文理由**(2026-10-03 起索引就带了,本文件此前漏记)。
  `quality=unverified` 靠它分得出"没验过"与"验了但判不了";
- `manifest_status` / `manifest_warning_count` / `manifest_warnings`:运行清单的警告状态与原文
  (2026-10-04 加,详见 §3.4 的补记)。**只透出、不参与判定** —— 不改 `quality`,
  也不改下面的默认排除集;`absent` 表示这条压根没有清单段(历史产物),不是缺陷。
  **(2026-10-09 补:这三栏不是每行都有键)** 只有走 `_quality_of()` 的 case01 成品行带;
  case00 痕迹行、`run.json` 读不出来的行、`unreadable` 行**整个键不存在**(它们额外给一个
  `error` 键说明原因)。所以"取不到这一栏"有两种成因,别都当成 `absent` —— 前者是没查/读不出,
  后者是查了、这条确实早于清单落地。要区分就看 `error` 与 `quality`。

**默认行为**:`/api/runs` **不返回** `questionable` / `debug` / `deprecated` / `unreadable`
(2026-10-09 订正:此前这里漏写 `unreadable`,而代码的排除集 `live/history.py:314` 一直有它)
—— 但不静默,响应里带 `excluded{count, runs[], reason}`;要全量加 `?include_questionable=1`。
平台**不要**把"少给了"当成"没有这条记录":以 `excluded` 为准。

### 3.2 信息边界(硬约束)

- `GET /api/run-detail/{source}/{id}` **默认只回专家可看的白名单**
  (`run_id / 日期 / turns / retrievals / events / state_history / final_feedback /
  audit / condition_monitor / reflection / router`),并标 `view: "expert-safe"`;
- **不得进专家视图**:`injector`(Branch 实验元信息 + 逐节点 dialogue 原文)、
  `branch_action`、`consistency`、`debug`、`quality`、`branch` 标签 —— 与 0904doc 04 六.3 /
  《Governance平台对接说明》§2.3 一致;
- 专家的 `View Full Context` 走**自然语言全文**(5002 的 `/api/runs/{id}/full-context`,
  或 5010 `/embed/review` 的对应页签),该文本**不含任何实验元信息**(有守卫测试);
- **原始 Reflection 不得被平台/专家覆盖**(只读数据源)。
- 平台若确实需要原始全文(内部排查),显式用 `?raw=1` —— 请**不要**把 `raw` 视图喂给专家页。

### 3.3 三种 source 的形状**不同**(按 `view` 分支,别只按一种写渲染)

`/api/run-detail/{source}/{run_id}` 现在**每种 source 都给 `view`**,用它判断你在渲染哪一套:

| source | view | data 的形状 |
| --- | --- | --- |
| `review`(case01 成品) | `expert-safe`(要原始全文用 `?raw=1` → `raw`) | 九块白名单:`turns/retrievals/events/state_history/final_feedback/audit/condition_monitor/reflection/router` 等 |
| `checkpoint`(case00 痕迹) | `case00-archive` | `{conversation, shots}` |
| `compressed`(压缩成品) | `compressed-index` | `{files}` |

**只有 `review` 有九块**(只有它出自 case01 的成品 `run.json`)。`/api/runs` 的行同理由
`source` 区分:`compressed` 行的 `case_id` / `engine_id` 为空(它不是一次受控实验)。

**另一条运行方式的产物不是九块**:实测 `case_engine run case01_stock --engine experiment-eval`
写出的是 `<case_id>_exp.json`,键只有 `branch/consistency/engine/run_type/scenario/state/timeline`。

若要把运行方式的产物也接进平台的列表,得先做一层映射(或让运行方式直接产出九块形状)。

### 3.4 时间字段的语义(别把剧情日期当成运行时间)

| 字段 | 是什么 |
| --- | --- |
| `start_date` / `end_date` | **模拟剧情日期**(如 `2026-08-27`),不是这次跑的真实时间 |
| `run_id` 里的 `<YYMMDD>` 与 `-<HHMM>` | **本地墙钟**(生成那台机器的本地时间,不含时区) |
| `manifest.created_at` | **带时区**的 ISO(`2026-09-22T18:28:10+0800`)—— 要跨机比真实时间就用它 |
| 专家标记的 `marked_time` / `marked_at` | 前者本地墙钟;后者带时区(2026-09-24 起) |

`manifest`(因此只有那一条有带时区的运行时间);其余记录的"什么时候跑的"只能从 `run_id` 的本地
墙钟近似。
补记(2026-10-04):生产路径(`python -m case01.run` → orchestrator)现在也在**落盘前**挂
manifest,`engine_id=case01-run`,并如实区分 `branch_mode`(preset/judge)与判定后端

`/api/runs/{run_id}` 这条路由**不在 5010 上**(它注册在 `case01/serve.py:149`,属 5002);
5010 的详情面是 `/api/run-detail/{source}/{run_id}`,而它**默认就是专家安全白名单**
(`live/history.py:580` → `expert_safe_record()`),这三栏按边界**不进**详情。逐面实况:

| 取数位置 | 带这三栏 | 依据(2026-10-09) |
|---|---|---|
| 5010 `GET /api/runs`(列表每条索引) | ✅ | `live/history.py:_quality_of()` 显式透出;实测 `demo1015-B` = `clean` / `0` / `[]` |
| 5010 `GET /api/run-detail/review/{id}`(默认专家安全) | ❌ | 白名单不含;实测 `data` 里无这三键,也无 `quality` |
| 5002 `GET /api/runs`(列表) | ✅ | `full_context.list_runs()` 每条走 `quality_of(rec)` |
| 5002 `GET /api/runs/{run_id}`(详情) | ✅ | `case01/serve.py:176` 把 `**fc.quality_of(rec)` 展开进 meta |

⇒ **平台侧要按"复现指纹"筛记录,只有两条路:5010 的列表面,或 5002 的列表/详情。**
5010 的详情面拿不到这三栏不是漏项,是 `quality`/实验元信息不得进专家视图的同一条边界
(`quality` 本身在 5010 详情面同样取不到,只在列表面给)。
用法上的口径要说清楚:这三个字段是**透出**,不是判定 —— 它们**不改 `quality`、不改默认排除集**。
一条 `manifest_status=noted` 的记录可以照样是 `ok`(规则判定没有采样温度、preset 没配判定后端
这类警告是"如实描述");反过来 `absent` 也不代表有问题,只代表这条是 2026-10-04 之前的产物。
要筛"复现指纹不可信"的,看 `manifest_status=error`(清单自身生成失败)。

### 3.5 主键与取值口径
- Router issue 的 `id` 是 **run 内序号**(`issue-1`…),跨 run 会重名。
  问题关联用 `(run_id, issue_id)`；专业任务首次建单唯一键为
  **`(source, run_id, issue_id, expert_category_id)`**，重审还须区分审核批次。
  同一问题的主、次专业分别建单，各自审核；具体规则见下节。
- `risk` 取值**小写** `low` / `medium` / `high`(平台比较时忽略大小写即可);
- `run_id` 命名:`<真实日期 YYMMDD>-<kind>-<case>-<engine>-<branch>[-HHMM]`,
  `kind ∈ {live, demo}`;judge 模式分支未知时名字里写 `auto`,**以记录里的 `branch` 为准**。

### 3.6 审核交接包（2026-10-05 已实现）

平台先用 `GET /api/runs?source=review` 发现记录，再请求
`GET /api/review-package/{run_id}`。该接口注册在 5010 共享历史路由中，当前运行
case00 或 case01 均可读取已落盘的 Case01 Run。它没有 `raw` 模式，不调用模型，
不写文件、不产生任务、不分配专家。

成功响应为 `{"ok": true, "data": {...}}`。OpenAPI 中的 `ReviewPackageResponse`、
`ReviewPackage`、`TaskCandidate` 和 `ManualTriage` 提供机器可读字段结构。

| data 字段 | 语义 |
| --- | --- |
| schema_version / source / run_id | 当前结构版本 `1.0`、固定 `review`、磁盘 Run 目录标识 |
| status | `ready`：候选可交平台建单；`manual_triage`：存在人工分流待办；`blocked`：禁止自动建单；均不表示专家已审核 |
| task_candidates | 主/次专业去重展开的候选，含 issue_id、expert_category_id、summary、risk、routing_reason、证据原文及句子 ID |
| task_candidates[].key | 四元素数组 `["review", run_id, issue_id, expert_category_id]`，平台用于幂等建单，不能把数组用不转义的字符串拼接 |
| manual_triage | 带稳定 key、issue_id、reason 的分流待办；可以和有效候选同时存在，平台须同时导入，不能漏掉待办后直接归池 |
| blocked_reasons | 被排除记录、缺反思、反思失败、缺最终反馈的原因码；blocked 时无候选、无正文。**四个码是字符串、平台要按字符串判**(2026-10-09 补,此前只给语义没给字面量):`run_not_reviewable`(这条的 `quality` ∈ `questionable`/`debug`/`deprecated`/`unreadable`,即索引默认排除的那四类 —— **交付主局 `demo1015-A`/`demo1015-C` 实测就是这个码**,HTTP 仍 200、`status=blocked`、`task_candidates` 为空)、`reflection_missing`、`final_feedback_missing`、`reflection_failed`(`reflection.quality.status=error`)。**583 条全量实测分布**:`ready` 474 / `manual_triage` 40 / `blocked` 69;原因码 `run_not_reviewable` 69、`reflection_failed` 5(这 5 条同时都是 `run_not_reviewable`,没有独立成因为它的记录),`reflection_missing`/`final_feedback_missing` 当前 0 条。原因用通用词、不含分支取值,与信息边界同一条线 |
| expert_pool_version / expert_categories | 当前类别目录版本与类别快照；具体专家账号仍由平台管理 |
| router_pool_version | Run 生成时的目录版本；旧记录没有此字段时为 null |
| snapshot / full_context | 专家安全结构化快照与自然语言全文；blocked 时分别为 null / 空串 |
| record_revision / category_revision / revision | SHA-256 内容指纹：安全记录、类别目录、完整交接包；响应 ETag 为带双引号的 revision |
| ownership | 明确 tasks / reviews 由 governance_platform 管理 |

同一内容重复读取的 revision 相同，不使用请求时间生成版本。平台初次导入按
key 去重；已有任务遇到 revision 改变时，应保留旧快照并显式处理新审核批次，
不能覆盖正在审核的内容。类别目录即使忘记提升版本号，内容变动也会改变指纹。
指纹用于版本识别，不是数字签名或审核完成证明。接口不实现条件请求 304。

异常分流原因包括 `router_error`、`router_skipped`、`router_empty`、
`router_missing_or_invalid`、`category_version_mismatch`、
`issue_id_missing`（该条 issue 缺 id 或 id 为空白）、
`issue_ids_duplicated`（多条 issue 撞同名 id；此时 `manual_triage` 项额外带
`conflict_id` 指明被重复的 id）、`issue_invalid`、`issue_fields_invalid`、
`category_unmatched_or_invalid`。缺 id 与撞名分开报：前者是字段缺失（补字段即可），
后者是 Router 产出了两条同名问题（应回退重跑 Router）。无 Router ID 的旧 issue 可按类别名称/别名精确
匹配；明确无效的类别 ID 不会被名称掩盖。任何一个次专业无效时，该 issue 整体
转人工分流。`reflection-review` 是全文人工分流锚点，不是自动通过的任务。

HTTP 404 表示 Run 不存在或非法路径（包括指向数据根之外的符号链接）；422 表示
记录/目录格式错误或文件内 run_id 与目录不一致；503 表示文件暂不可读。
这些响应为 `{"ok": false, "error": "原因码"}`，不输出本机文件路径或异常堆栈。
业务上的 blocked 返回 HTTP 200，平台必须检查 `data.status` 后再建单。

## 四、平台侧要实现的流程(状态机)

按 04 七/八、05 四实现，详细执行规则见
[专家审核流程补充规范](专家审核流程补充规范.md)。以下为平台侧待实现流程，
本仓提供问题与原文，不代表专家分配和审核已经上线：

```
Reflection + Router issues → 每个问题＋专业类别建单 → 首轮两人独立审核
  路由异常 → 人工分流            人数不足 → 待调度，保留轮次和缺口
  一致/协调确认 → 定稿           实质冲突 → 追加三位新人，累计五份意见
                                  至少三票一致 → 多数结论
                                  2/2/1 → 人工裁决，明确标记
全部任务定稿且改文确认 → 材料 ready → 持久化成功后 pooled
```

- 每个 issue 的专家意见 = Approve(反思核心成立)/ Edit(有遗漏或表述问题,只改该片段)/
  Reject(核心逻辑不成立);
- 一个 issue 的 `expert_category_id` 与 `secondary_expert_category_ids` 去重后，
  每个类别各建一条任务，共享 Run 与原始 Reflection；不按合并前 ID 重复建单。
- Router 失败、issues 为空、unmatched 或字段不全时进人工分流，不自动通过。
- 原始 Reflection、每人意见、修改版本、最终结论及少数意见独立保存。
  多数 Edit 不等于最终改文已确认；具体确认门槛见补充规范第 5 节。
- 归池保存完整治理材料，包括被否决内容及其理由；归池不自动批准或执行训练。
