## 一、一句话定位

Provenance 是一套**声明式场景驱动**的"组合 → 运行 → 展示"平台：用一份 `scenario.yaml`
声明场景，由 `case_engine` 引擎把它跑成可审计的运行记录，再经统一数据契约
（`/api/runs` + `/embed/explore`）和可视化面（Phaser 小镇 + 结果面板）对外展示。
对外只暴露**一个实时入口 `http://<host>:5010/`**，供治理平台用 iframe 嵌入。

三套仓库的分工：

| 仓库 | 角色 |
|---|---|
| `D:\zzr\provenance` | 场景引擎（`case_engine`）、三个声明式场景（cases）、case01 注入器、case00 冻结容器、统一数据/可视化面、live_switch 进程管理 |
| `D:\zzr\mavis\mavisframework` | 多智能体运行时，负责角色 think 编排（移动/计划/感知/反应/反思）、世界钩子、插件面 |
| `D:\zzr\mavis\config_tool` | 组合配置工具：管理组合注册表，`/api/run/execute` 执行运行并异步切换 5010 实时面 |
| `D:\zzr\provenance\packages\mavis-vizkit` | 可视化插件包（Phaser 小镇 / report / live / town），可复用于多案例 |

## 二、核心概念

### 2.1 场景（Scenario）= 一份 YAML，纯数据
场景是引擎的输入，也是"新增一个案例 = 写一份 YAML，零代码"的载体。
每个场景在 `provenance/cases/<case_id>/scenario.yaml`：

| 段 | 含义 | 例子 |
|---|---|---|
| `meta` | 场景 id、名称、说明、推荐引擎、剧情起止日期 | `engine: experiment-eval` |
| `roles` | 角色清单（`ai_tool` 会表达 / `user` 提问方），含 llm、temperature、conflict_rules | Ethan Lin（user）、Investment AI（ai_tool） |
| `world.state_schema` | 可变世界状态字段的 schema（initial + type） | `approved: {initial: false, type: bool}` |
| `world.value_tendency` | 价值权重（制度层 governance + 个人起点 initial_tendency），`sandbox-value` 预检真读取 | — |
| `branch` | 分支判定规则（`experiment-eval` 消费）：default + 词表 → 分支 A/B/C | — |
| `consistency` | 一致性扫描信号词（buy / cond / negators / neg_phrases） | — |
| `reflection` | 反思段：`system_prompt`、`prompt_cn`、`fb_asker_key` | — |
| `router` | 问题分流配置（judge_prompt 等） | — |
| `timeline` | 声明式时间线：branch_map、t0、lines（A/B 线日期事件）、interactions（首末节点交互模板） | — |
| `retrieval` | 检索配置 | — |
| `inputs.sample_answers` | 受判对象回答样本（experiment-eval 空输入时自检兜底） | — |

现有三份场景：
- `cases/case00_village`：原初 6 角色投资咨询小镇（冻结留档，推荐引擎 `sandbox-value`，含治理价值权重）
- `cases/case01_stock`：2 角色（Ethan + Investment AI）、节点驱动受控实验（推荐引擎 `experiment-eval`，含 timeline A/B/C 三线）
- `cases/case02_minimal`：中性主题（新业务立项审批），证明"场景引擎与案例无关"

### 2.2 引擎（Engine）= 可注入、可组合的运行策略
`case_engine/engines.py` 是注册表与工厂，`strategy.py` 是策略实现。核心思想：
**同一场景可与不同引擎自由搭配**（运行时 `requested` 覆盖推荐），`supports(scenario)`
判定"这个引擎能不能跑这份场景"。

| 引擎 id | 名称 | 组件 | 产出 |
|---|---|---|---|
| `experiment-eval` | 受控实验 / 评估 | scene, chat, reflection, overview, events, state, retrieval, router, injector, audit | `run.json`（分支 + 反思 + 一致性 + 检索） |
| `sandbox-value` | 生成式价值权重沙盒 | scene, chat, governance, timeline, reflection | checkpoints（simulate-*/value_tendency） |

**组件清单**（`_COMPONENTS`）是"该引擎激活哪些面板"的声明，由各服务（case00/01 实时面）
折叠成具体渲染。这正是 M3 的落点：面板显隐由引擎决定，而非写死布尔。

### 2.3 运行（Run）= 可审计的记录
一次运行产出**带分支后缀**的记录目录，命名：`<YYMMDD>-<kind>-<case>-<engine>-<branch>[-HHMM]`
（如 `260917-demo-case01-mavis-A`）。**目录名必须等于记录里的 `run_id`**（不一致会导致 5002 契约与结果面板显示成两个名字）。

## 三、整体架构

```
┌──────────────────────────── 编排 / 配置侧 ────────────────────────────┐
│  config_tool (mavis/config_tool)                                       │
│    组合注册表 ── /api/run/execute ──► 执行 → 异步调 live_switch 切换 5010 │
└───────────────┬────────────────────────────────────────────────────────┘
                │  live_switch.py（provenance）
                │  按「命令行特征 + ppid 折算实例」管理 5010 归属
                ▼
┌──────────────────────────── 实时 / 展示侧（5010 单入口）───────────────┐
│  5010 实时面（case00 或 case01，互斥）                                   │
│   ├─ 场景推演线程（Ollama qwen3:4b）                                    │
│   ├─ /embed/scene · /embed/goals · /embed/timeline · /embed/explore     │
│   └─ include_router( live/history.py )                                  │
│        ├─ GET /api/runs        （聚合三处历史 → 统一摘要）               │
│        └─ GET /embed/explore   （数据界面：左侧 Menu + 右侧详情）        │
└───────────────┬────────────────────────────────────────────────────────┘
                │  WS:  agent 实时坐标 / chat_line / snapshot
                ▼
┌──────────────────────────── 数据 / 只读侧 ─────────────────────────────┐
│  case_engine（声明加载 + 分支路由 + 一致性 + 反思 + 检索 + 时间线装配）   │
│  └─ 产物落盘：                                                        │
│       case01/runs/<id>/run.json        （case01 成品）                  │
│       results/checkpoints/<name>/      （case00 痕迹）                  │
│       results/compressed/              （压缩成品）                      │
└───────────────────────────────────────────────────────────────────────┘
```

**分层原则**：数据与渲染分离。场景是纯数据，引擎是策略，可视化面是独立插件包，
三处历史数据由唯一聚合端点归一化，不迁移、不重写。

## 四、进程与服务清单

| 服务 | 端口 | 是否跑模拟 | 用途 | 启动 |
|---|---|---|---|---|
| 实时面（case00） | **5010** | 是 | 6 角色小镇 + 治理面板 + 干预时间轴 + 数据界面 | `live_switch.py --start case00` |
| 实时面（case01） | **5010** | 是 | 2 角色注入器推演（小镇 + 结果记录九块） | `live_switch.py --start case01` |
| case01 只读契约 | 5002 | 否 | `/api/runs`、`/api/runs/{id}`、`.../full-context` | `case01/serve.py` |
| case00 存档只读 | 5003 | 否 | `/api/runs`、`/api/runs/{id}`、`/` | `case00/serve.py` |

**关键规则**：
- **5010 是唯一实时入口**，case00/case01 在此端口**互斥**（同时只起一个实时面）。
  瓶颈是只有一个本地 Ollama（`qwen3:4b-instruct-2507-q4_K_M`），两套推演同跑会互相拖慢。
- 只读面（5002 / 5003）不跑模拟、**可随时全开**。
- **进程归属靠命令行特征 + ppid 折算，不靠端口**——uv venv 的 python.exe 是 trampoline
  （一个实例父子两个 PID），只看端口会发现不了第二份游离实例。`live_switch --start`
  起完会校验端口真的绑上，没绑上就收掉新进程，**绝不留游离实例**。
- `live_switch.py --status` 能区分 case01 三种状态：在推演 / 在听（已跑完）/ 仅审阅
  （靠 5010 `/health` 的 `finished` / `finish_reason`，不靠猜）。

常用命令（在 `provenance/provenance` 下）：

```
python live_switch.py --status                      # 只看现状
python live_switch.py --start case01 --nodes 2      # 起 case01（自动先停 case00 与本 case 旧实例）
python live_switch.py --start case01 --review-only  # 不推演，只起"小镇+结果记录"界面（不占 Ollama）
python live_switch.py --start case00                # 切到 case00
python live_switch.py --stop all                    # 全停实时面（不碰只读面）
```

## 十、`live_switch` 进程管理（机制细节）

`provenance/provenance/live_switch.py`：

```python
LIVE = {"case00": 5010, "case01": 5010}   # 5010 唯一实时入口，两 case 互斥共用
CMD_NEEDLE = {"case00": "live_fastapi.py",
              "case01": "vizkit.live_run"}
```

- **归属识别**：按命令行的 `CMD_NEEDLE` 特征认进程（防误判），按 ppid 折算 uv venv
  trampoline 的父子双 PID 成"实例数"，>1 即报 `[!] 有 N 个实例`。
- **归属排它**：`--start caseX` 先停另一个 case 的旧实例、再停本 case 的旧实例（防游离），
  然后起新进程并校验端口真的绑上；没绑上就收掉并报错。
- **不误停只读**：`--start case00` 不会误停一个"仅审阅"的 5010（它没在推演、不抢 Ollama）。

## 十一、对接指南（面向治理平台）

可视化经 iframe 嵌入 Tongmu 治理平台。**平台只需要一个地址**：

```
http://<host>:5010/
```

### 11.1 可嵌入面清单

| 嵌入面 | URL | 说明 |
|---|---|---|
| 完整界面 | `http://<host>:5010/` | 小镇实时 + 右栏结果记录卡片（可折叠） |
| 纯场景 | `http://<host>:5010/embed/scene`（或 `/?embed=scene`） | 只嵌 Phaser 场景，不含面板/结果卡片 |
| 结果面板（压缩版式） | `http://<host>:5010/embed/review`（或 `?embed=1`） | 去掉大标题与页边距，贴合 iframe |
| 数据界面 | `http://<host>:5010/embed/explore` | 历史 run 浏览 |
| 治理面板（case00） | `http://<host>:5010/embed/goals` | 权重调整（case00 专属） |
| 干预时间轴（case00） | `http://<host>:5010/embed/timeline` | 专家参与记录（case00 专属） |

等价写法：`?embed=scene` 与 `/embed/scene` 同效，嵌入方不改路径也能只取场景；
结果卡片只在独立首页出现，嵌入面不带。

**深链**：`?run=260917-demo-case01-mavis-A&tab=router` 指定默认记录与页签。
页签 id：`overview` / `turns` / `retrievals` / `events` / `states` / `reflection` /
`router` / `injector` / `audit`。

**WebSocket**：场景页的 WS 是 `"ws://" + location.host + "/ws"`，**按 location 拼**，
所以嵌到哪个端口都连得对（iframe 不改变它自己的 location）。

### 11.3 对接实现建议（双后端、单向只读）

已定结论：**Tongmu 治理平台与 Provenance 各留一个后端，不做进程合并；用"只读接口单向拉取"
接起来。** Provenance 不感知 Tongmu 的存在，Tongmu 用自己的库落专家审核流程。

1. **嵌入**：用 `<iframe src="http://<host>:5010/embed/scene">` 嵌场景；
   `<iframe src="http://<host>:5010/embed/review">` 嵌结果。iframe 无缝因为本栈
   **不带 `X-Frame-Options` 与 CSP**（测试钉死，带上就白做）。
2. **建单**：Tongmu 轮询/订阅 `/api/runs`，发现新 `run_id` 即建一条专家审核单，
   记录落到自己库。
3. **取详情**：拉到详情页签数据用于专家审 Expert 对照（reflection + router.issues）。
4. **信息边界**（固化口径）：
   - `risk` 字段用小写（`low/medium/high`），审核侧按此收敛；
   - 复合主键 `(run_id, issue_id)` 唯一；
   - 专家审核意见**不得覆盖/改写**原始 Reflection 记录（只读数据源）。
5. **运维**：5010 由运维用 `live_switch.py` 起/停；平台只负责引地址，**不必知道**
   当前跑的是 case00 还是 case01。若平台只想看结果而不要推演，运维可用
   `live_switch --start case01 --review-only`（只起界面、不占 Ollama）。

### 11.4 每条嵌入面都不可加的安全头

- 上述所有 `/embed/*`、`/`、数据接口**都不带** `X-Frame-Options` 与 CSP——加上则 iframe 失效。
- 这是测试里钉死的约束，改动服务时要保持。

### 11.5 已知对外注意（待确认项）

- **CDN 依赖**：Phaser / Bootstrap 走外部 CDN。若 Tongmu 部署环境**无外网**或要强隔离，
  需把这些库自托管到 `/static`。是否本地化取决于对方网络策略，属架构选择而非缺陷。
- **一台机器一个实例**：5010 是单实例实时入口，若 Tongmu 需高并发拉取，可用只读面
  （5002/5003，可多开）承载读压力；实时面保持单实例。
