# Expert Review 专家审核流程补充规范

> **状态**:现行
> **最后核对**:2026-10-05
> **说明**:补足 GTC《04｜Reflection → Governance Platform 技术集成流程》的建单、分配、裁决、归池与审计执行规则；平台侧实施依据

## 0. 范围与现状

本文细化上游《04｜Reflection → Governance Platform 技术集成流程》的第五至十节，
不改变其核心要求：每个“问题＋专业领域”首轮由两位不同专家审核，发生实质冲突时
追加三位新专家，保留全部意见与原始 Reflection。若本文与上游研究决策冲突，
应先修订本文并记录决策，不能让平台实现自行解释。

**本文是实施规范，不代表功能已经上线。**截至 2026-10-05，`provenance` 提供
Router 专家类别目录、问题及原始 Reflection 的只读数据；具体专家人员、任务、
分配、审核和归池由 Governance Platform 管理。5010 对接入口仍以
《平台对接契约_5010唯一入口》为准。

## 1. 建单与路由异常

### 1.1 建单资格

平台仅从 `source=review` 的已完成 Case01 Run 建审核任务。先读取 5010
`GET /api/runs`，再读取 `GET /api/run-detail/review/{run_id}` 的专家安全视图。
平台不得把 `checkpoint`、`compressed` 或运行中的记录当成已完成的 Case01
Reflection 审核任务。列表默认排除的 `questionable`、`debug`、`deprecated`、
`unreadable` 不自动建单；排除数量与原因应保留在导入日志中，供管理员核查。
`reflection.quality=pass` 只表示自动文本检查通过，不等于专家审核通过。

### 1.2 任务粒度与幂等键

一个 Router issue 可以对应主专业 `expert_category_id` 和若干
`secondary_expert_category_ids`。平台为**每个不同的“issue＋专业类别”**建一条
`Expert Review Task`，共享同一个 Run 和同一份原始 Reflection；不同专业的意见
分别审核、分别定稿，不自动互判为冲突。

- 平台任务可使用自己的不可变 `task_id`；建单唯一约束为
  `(source, run_id, issue_id, expert_category_id)`。
- `issue_id` 仅在 Run 内唯一，不能单独作全局主键。次专业 ID 去重，若与主专业相同则忽略。
- `merged_from_issue_ids` 是 Router 合并留痕，不能据此再次建单。
- 重复拉取同一 Run 必须幂等；建单时保存 Router 类别目录版本、问题摘要、风险、
  路由理由、证据引用和原始 Reflection 快照。上游记录后续变化不能静默改写已审核任务；
  如确需重审，应新建带版本号的审核批次并关联旧批次。

### 1.3 异常与人工分流

若 Reflection 已生成而 Router 失败、`issues` 为空、类别 `unmatched`、类别
ID 不在目录中，或必要字段缺失，平台仍保留原文并创建一条**人工分流待办**，
不伪造专业任务，也不把它当作“无问题已通过”。待办记录失败原因、Run、
Reflection 和 Router 原始状态。管理员可从现有类别目录选择一个或多个专业后建单；
这一动作需记录执行人、时间和理由。不能匹配时保持待办并提示研究侧补类别。

## 2. 专家池与首轮分配

### 2.1 平台管理的专家资料

5010 的 `GET /api/expert-categories` 只提供**类别**。平台须持有具体专家账号、
所属专业类别、可接单状态、接单上限，以及与任务有关的利益冲突/回避标记。
任务按 `expert_category_id` 匹配专家；使用目录版本快照，避免类别改名后历史任务
失去解释。具体专家身份不得写回 `provenance` 的 Run 记录。

“当前可用”至少同时满足：账号有效、具备该任务的专业资格、未回避本任务、
未在该任务任何轮次提交或被分配、当前接单量未超过平台设定的上限。
平台可在合格名单内随机或按负载选择，但必须记录选择方式及当时的候选人数；
不得预先写死专家姓名。分配同一任务时加事务或等效并发保护，确保两人不同、
每个专家在该任务全轮次至多占一个名额。

### 2.2 分配、拒接与人数不足

首轮为同一任务分配两位不同的可用专家，记录 `round=1`、分配时间、截止时间、
分配人/系统主体和状态。专家只能读取自己被分配的任务，提交时由平台账号确定
`expert_id`，不能信任浏览器传入的任意专家 ID。

专家拒接、超时或经管理员确认回避时，原分配记录标为 `declined`、`expired` 或
`recused`，保留原因与时间，再从同专业合格名单中补一位**未参与过该任务**的专家；
已提交的意见不得删除或覆盖。未收到两份有效首轮意见前，任务保持待审，
不得进入冲突判断。

若同专业可用人数不足两人，任务进入 `assignment_blocked`，显示缺少人数和原因，
通知平台管理员补池或协调研究侧调整专业归属。不能让同一专家占两个首轮名额，
也不能默认跨专业借人。任何人工改派都记录原类别、新类别与批准理由。
