### 三个要说清的结论

1. **"内化"这一环在 case01 线没有载体。** IVD 的名字来自"决策→后果→反思→内化",而 case01 的产物是:
   判定留痕 + 对手方资金后果 + 反思正文 + 问题分流。**价值倾向不会随后果变化** ——
   倾向更新只在 case00(6 角色小镇)那条已冻结的线里。对外讲 IVD 时,要么把 case00 一起摆出来,
   要么就说清"这条线演示的是判断与后果,不是倾向内化"(否则是过度声明)。
2. **可复算只覆盖最新一局。** `manifest`(git commit / 运行方式 / 判定后端与模型 / 温度 / 各哈希)
   只在 `260922-live-case01-mavis-auto-1820` 这一条里有;**其余 27 条不可复算**(当时决定不回填)。
3. **判定重试留痕只在代码里,没在记录里验证过。** `LLMBranchJudge` 现在会带
   `attempts`/`raw_outputs`,但现有 16 条 judge 记录都是改动**之前**跑的,记录里只有
   `detected/reason/judge/answer_head` —— 这套留痕**从未在真实记录上跑通过**。

## 二、能不能对接平台侧

**结论:只读演示可以对接;专家写回(feature 全量)不行 —— 差一个受控词表和一层鉴权。**

现在就能给的(已核对过):
- 唯一入口 `5010` + 嵌入面(`/embed/scene`、`/embed/review`、`/embed/demo-parent`)+
  `GET /api/runs`(含 `quality`/`excluded`/`ignored_params`/分页)+ `GET /api/run-detail`(默认专家安全视图);
- 建单要读的字段**齐**:123 条 issue 里只有 4 条缺 `routing_reason`,其余
  `id/summary/risk/risk_note/field/style` 全有;`risk` 是小写 `high|medium`。

**四个卡点(按严重度)**:

1. **`issue.field` 没有受控词表 —— 这是硬卡点。** 123 条 issue 用了 **115 个不同取值**
   (`行为金融学` / `行为金融学专家` / `行为金融学与市场情绪建模` …)。
   平台侧的流程是"按 `issue.field` 匹配专家池"(见对接契约 §四),这种自由文本**没法建池**。
   得先定一份固定领域标签(建议 8–12 个),在提示词与校验里约束,历史记录给映射表。
2. **没有鉴权** → 平台侧只能读,不能写回(改约束/标记反思)。要写回必须先加一层
   (反向代理 basic auth 或平台侧签名 + 审计),不能拿"绑本机"当边界。
3. **嵌入面下拉含 questionable 记录**:平台侧要自己拿 `/api/runs` 的 `run_id` 做白名单。
   要么我们在嵌入面支持 `?quality=ok`。
4. **没有事件推送**:宿主只能轮询(已写进对接文档);另外记录里**没有"这一局属于哪个模拟会话"**
   的字段(`simulation` 关联只在服务端状态里),平台要把任务挂回某一场演示时缺个抓手。

**一句话**:平台侧今天就能把"小镇 + 结果记录"嵌进去、把 issue 建单;但「专家池」和
「写回」这两步,**卡在词表与鉴权上**,不是卡在接口上。

## 三、实现侧待办(按优先级,每条都给验收)

**P0 —— 卡住对接的**

1. **`issue.field` 受控词表**:定标签集(研究侧定口径)+ 提示词约束 + 落盘校验;
   历史 123 条给一张"旧值 → 标签"的映射(或标 `legacy`)。
   验收:新跑的记录里 `field` 100% 落在标签集内;给平台侧一份标签清单。
2. **嵌入面质检过滤**:`/embed/review?quality=ok`(或按 `run_id` 白名单)。
   验收:嵌入面下拉里不再出现 questionable/debug。
3. **判定重试留痕落地**:确认 `attempts`/`raw_outputs` 进 `run.json`(代码已有),
   **跑一局真实记录**验证。
   验收:新记录里 `branch_action.judge_info` 含 `attempts` 与 `raw_outputs`。
4. **写回鉴权(若平台要专家写回)**:反代 basic auth 或 token + 审计留痕。
   验收:不带凭证的写请求被拒;带凭证的写请求在 `audit` 里留痕。
5. **`routing_reason` 补空**:123 条里 4 条为空(旧跑,提示词加要求之前)。
   验收:新记录 0 条空。

**P1 —— 可复算与可解释**

6. **`manifest` 覆盖**:历史 27 条不回填的话,至少在记录或索引里**标注"不可复算"**,
   别让平台以为每条都能复算。验收:`/api/runs` 能区分"有清单/无清单"。
7. **`simulation` 关联**:记录里记下这局属于哪个 live 会话。验收:能从记录反查会话名。
8. **`/api/explain` 扩到 case01 面**:现在可解释性面板只挂在 case00 面;
   case01 的"为什么"要翻九个页签才看得到。验收:case01 面也有一页因果(检索→判断→后果→反思)。

**P2 —— 工程与收敛**

9. 两个实时面的宿主协议对齐:case00 面只有"角色点击 → 发宿主"这条单向消息,case01 是双向协议。
10. 可观测性:288 处 `print` vs 8 处 logger、时间戳无时区;看门狗;**一键起停**(现在四个面靠手工)。
11. `case01` 与 `case_engine` 重复实现收敛(consistency 177 vs 164 行、reflection 509 vs 496 行);
    死代码(`run.py`/`render.py`/`viz.py` 引用 0 处)清理前**先补导入面测试**(上次误删 `viz.py` 的教训)。
12. **人工金标**(判定准确率、同输入一致性、反思/问题拆分质量):需要研究侧标注,实现侧出工具。
