## 一句话

机制面已经够用(五条 IVD 不变量里四条实测成立),现在**卡在"闭环"上**:
判定语料只有六成走 agent 判断、"内化"这一环在 case01 没有载体、
平台侧拿到 `issue.field` 却建不了专家池。
所以下一步顺序是:**先把研究闭环打通 → 再补内化 → 最后收工程底座**,不要反过来先做界面。

## 方向 A:让"决策由 agent 产生"在语料上成立(P0,最该先做)

**现状**:`branch_source` 实测 `judge` 16 / `preset` 12 —— 43% 的记录里分支是运行参数给的,
这批语料本身不构成"决策由 agent 产生"的证据。守卫有"同场景两种回答 → 两个分支"的反事实测试,
但**没有一条真实记录**这样做过对照。

**做什么**
1. 用默认 `judge` 模式跑够样本(建议 ≥ 10 局),`preset` 只作对照条件;
2. 做**反事实对**:同一场景、同一时间线,喂两种显著不同的 T0 回答,记录成对保存并在索引里可辨;
3. 索引里把 `preset` 显式标出来(字段已有 `branch_source`,面板/契约里也要能一眼看出)。

**验收**:10 局里 `judge` 占比 ≥ 90%;≥3 组反事实对,两局分支不同且 `judge_info.reason` 可见;
`/api/runs` 能按 `branch_source` 过滤。
**依赖**:无(纯实现侧)。

## 方向 B:补 IVD 的"内化"环(P0,口径待研究侧拍)

**现状**:case01 记录 **28/28 零 `tendency`**;`state_history` 只有对手方资金/持仓。
价值倾向只在 case00(已冻结)那条线。也就是说"决策→后果→反思→**内化**"的最后一环,
在现在这条主线上**没有载体**。对外讲 IVD 时这是个会被问到的点。

**两条路,择一(研究侧拍)**
- **B1 把内化做进 case01**:最小可行 = 后果(盈亏、是否与 AI 的 T0 判断一致)写进内核倾向,
  且**下一局的检索与措辞受它影响**。关键:倾向归内核(mavis),案例侧只传后果,不直接改倾向。
- **B2 明确由 case00 承载**:case01 定位为"判断与后果",对外叙事按此切分,
  所有材料不再暗示 case01 有倾向内化。

**验收**:B1 → 同一角色连跑两局,第二局的检索/措辞能被第一局后果影响,且记录里查得到这条影响;
B2 → 文档、对接材料、演示口径统一,字面上不再出现"case01 展示内化"这类说法。
**依赖**:研究侧定"后果→倾向"的换算口径;B1 需实现侧改内核(只允许加法、默认关闭)。

## 方向 C:打通研究闭环(受控实验 → 专家审核 → 金标 → 训练材料)(P0,阻塞对接)

**现状**:平台侧**能建单**(123 条 issue 字段齐,只有 4 条缺 `routing_reason`),
但**建不了池**、**写不回**、**复算不了**、**没有统计出口**。

**做什么**
1. **`issue.field` 受控词表**(硬卡点):实测 123 条 issue 用了 **115 个不同取值**。
   定一份固定标签(建议 8–12 个),提示词里约束、落盘时校验,历史值给映射表或标 `legacy`;
   产出《字段标签清单》交给平台侧建池。
2. **写回鉴权**:平台侧若要专家改约束/标记反思,先加一层(反代 basic auth 或平台侧签名)+ 审计留痕。
3. **导出接口**:一条命令导出"标注包"(issue + 反思原文 + 判定留痕 + 该局 manifest),
   供人工金标与训练材料使用。
4. **N 局批量与统计**:同条件跑 N 局,输出分支分布、判定稳定性、问题条数、耗时。
5. **金标工具**:20–30 条判定与反思的人工标注入口与一致性计算。

**验收**:平台侧用标签清单能建池;导出包能被标注人直接读;`一条命令` 给出 N 局统计;
金标给出**准确率与同输入一致性数字**。
**依赖**:①词表口径(研究侧)②专家池字段(平台侧确认)③金标(研究侧标注)。

### P0(新增,排在所有 P0 之前):嵌入面把实验底牌露给了平台侧的专家

**现状**(实测,不是推测):

- `/embed/review` 与 `/review` 是**同一份页面**,只差一个 CSS class;页面把
  `判定方式` / `分支来源` / `T0 立场一致性` 三行**无条件**渲染(概览里还有 `branch` 字母)——
  代码注释写着"自相矛盾的记录必须自己说出来",那是给**我们自己复核**用的设计;
- 更关键的是取数接口:该页面用 `/api/review/run/{id}`,**返回原始 `run.json`**
  (含 `injector` / `branch_action` / `consistency` / `debug` / `branch`);
  而 `/api/run-detail` 的专家安全视图是对的 —— **边界只做在了一条 API 上**。

**后果**:平台侧一 iframe,它的专家就看到"这条是 A 线预设、T0 立场不一致"——
正是契约 §3.2 规定不得进专家视图的内容;而且没有鉴权,拿到 iframe 地址的人都能取原始 JSON。

**做什么**

1. `/embed/review` 进**安全模式**:不渲染 `branch` / 判定方式 / 分支来源 / T0 一致性,
   并隐藏"注入器"页签;`/review`(我们自己复核用)保持全量;
2. 页面取数改走安全视图:或给 `/api/review/run/{id}` 加 `?safe=1`,或直接换 `/api/run-detail`;
3. `/api/review/runs` 补 `quality` 字段,嵌入面据此过滤 questionable
   (现在面板列表里**根本没有 quality**,想滤也滤不了)。

**验收**:嵌入模式下**在浏览器里**看不到那三行与注入器页签(`case01/tools/webshot.js` 截图核对);
`/api/review/run/<id>?safe=1` 不含敏感键;面板列表带 quality 且默认不列 questionable。

**依赖**:**口径待定** —— "我们自己复核保留全量、嵌入面收紧"是否就是想要的切分,
需要契约/研究侧一句话确认;实现侧不擅自决定哪个字段算"专家可见"。

### P1(新增):反事实后果没有结构化,三线后果没法自动比

**现状**:没买的那两局,机会成本只写在 `final_feedback` 的自然语言里(如"股价后来涨了约 40%"),
`state_history` 只有资金/持仓,**没有基准价或错过收益字段** → 平台/研究侧无法自动比较
A 买 / B 不买 / C 条件化 三条线的后果。

**做什么**:在 `world.state_schema` 加结构化后果(如 `benchmark_price` / `missed_gain_rmb` /
`would_have_exited`),由事实层算,案例只声明口径(不变量 4:机制不算判断)。

**验收**:同一局三条线的记录里都有可比较的数值字段;面板能直接给出"三线后果对照"。
