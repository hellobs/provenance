## 一、结论先给

| 档 | 复现什么 | 现在能不能 | 前提 |
| --- | --- | --- | --- |
| ① 产物级复算 | 拿同一批 `run.json` 重算质检与一致性判定 | **能**(需要记录包,范围见 §二·补) | 附件记录包 + 本仓代码 |
| ② 设定级复现 | 确认这条记录跑在哪个 commit、哪份资料、哪版提示词、哪种判定后端 | **能,但只覆盖新记录** | 记录里有 `manifest` 段 |
| ③ 逐字重生成 | 在自己机器上重跑一次得到**同样的** T0 回答与分支 | **有条件能**:**同机、同一模型驻留、同一预热形态、单通道串行**下实测逐字节全等(2026-10-06 七条落三桶;2026-10-07 同桶内累计 **76/76 对全等**,并有一次**跨约 18 小时、跨 5 个 commit** 的复现成功)。**跨机/跨版本/跨状态/并发都不能** | 见 §五、§五·补 与 §五·补四;需要的是"跑法一致"而不是"更多记录" |
| ③·小镇 逐字重生成 | 在 5010 实时面上用**同一个种子**再跑一局,得到逐字相同的台词 | **实测做不到**(2026-10-06 三条真跑;连服务端状态对齐的那一对也不同,漂移从 T0 的**第一句台词**就开始) | 这一面能承诺的是 ②:**同种子会走同一条线、同一套事实、同一个分支判定;台词措辞不保证逐字**(哪些字段实测全等、哪些会漂,见 §五·补三) |

一句话口径:**输入与设定可核对;输出在"固定服务端状态"下可逐字重跑(仅批/单条路径)——固定 = 同机同模型 + 同驻留/预热形态 + 单通道串行;状态不固定、或改用并发通道,就不承诺逐字(2026-10-07 实测:同种子 3 通道 6 条出 6 种内容);小镇实时面一律只承诺"同一条线、同一套事实、同一个分支判定",不承诺逐字——任何情况下都不承诺"谁都能重跑"。**
这也与科研边界一致——本案例主张的是状态级内化与反思层证据,不主张行为级改变。

## 二、① 产物级复算怎么做

成品记录按仓约定**不入库**(`git ls-files` 里只有测试 fixture),所以复算用的是随附的**记录包**
(逐条 `run.json` + `SHA256SUMS.txt`)。**`SHA256SUMS.txt` 已生成(2026-10-05,覆盖 22 个文件)**;
**zip 亦已打**(2026-10-05,`demo-case01-20261015.zip`),`SHA256SUMS.txt` 留包根、
zip 自身的哈希另列(`.zip.sha256`)。本文钉住"拿到包之后怎么验、怎么跑",命令都在本机实测过。

1. 校验完整性(逐字节一致才继续)。Python 版对 CRLF 与自引用都容错:
   ```
   python -X utf8 -c "import hashlib,pathlib;
   [print(n, 'OK' if hashlib.sha256(pathlib.Path(n).read_bytes()).hexdigest()==s else 'MISMATCH')
    for s,n in (l.split()[:2] for l in pathlib.Path('SHA256SUMS.txt').read_text(encoding='utf-8').splitlines() if l.strip())
    if n != 'SHA256SUMS.txt']"
   ```
   想直接用 `sha256sum -c SHA256SUMS.txt` 的,前提是校验和文件写成 **LF**(Windows 上
   `print()` 会写成 CRLF,`sha256sum` 会把每行当成不存在的文件而全红)。
2. 解到任意目录,指给引擎(读侧 `case01/serve.py`、`live/history.py` 与写侧 `case01 run` 都吃这个变量):
   ```
   export CASE01_RUNS_ROOT=<解包路径>/runs
   ```
   **必须给绝对路径**(2026-10-05 起强制):相对值会在启动时报
   `AmbiguousPathError` 并指出该改成什么。此前相对值被静默按"当前工作目录"解释,
   同一配置换个目录启动就指向别处 —— 与其让复现结果莫名其妙,不如让配置错误当场可见。
   同理适用于 `CASE_ENGINE_CASES_ROOT` / `CASE00_CHECKPOINTS_ROOT` / `RESULTS_COMPRESSED_ROOT`
   及 config_tool 的 `MAVIS_*` 路径类变量。
3. 质检与索引口径(纯离线,不调模型,三条都实测可跑):
   ```
   python -X utf8 -c "from case01 import serve; print(serve.list_runs()['count'])"
   python -X utf8 -m case01.tools.consistency_report --runs-dir <解包路径>/runs
   python -X utf8 -m case01.tools.reflection_audit  --runs-dir <解包路径>/runs
   ```
   `reflection_audit` 只有 `--runs-dir`/`--clean`/`--write`(默认相对 `case01/runs`,**不认** `CASE01_RUNS_ROOT`),
   没有 `--check` 这个开关;它的判据是"结尾像不像完整句子",退出码 1 = 有疑似截断或读不了。
   `--clean/--write` 会改你的记录文件,复算时**别带**。

## 三、② 设定级复现怎么做

每条**新记录**的 `run.json` 里有 `manifest` 段,逐项可核对:

| 字段 | 是什么 | 你手上有的东西可以怎么验 |
| --- | --- | --- |
| `git_commit` | 跑这条记录时的仓 HEAD | `git rev-parse <sha>` 在不在你拿到的历史里 |
| `scenario_sha256` | `cases/case01_stock/scenario.yaml` 内容哈希 | 见下方一行命令 |
| `financial_data_version` | 检索资料目录的合体哈希 | 同上 |
| `prompt_versions` / `judge_prompt_version` | 反思/路由/判定提示词的 12 位哈希 | 内容改一个字符就会变 |
| `branch_mode` / `branch_source` | 分支是运行参数指定(preset)还是 T0 回答判定(judge) | **只有 `judge` 才是实验主路径**;`preset` 是对照条件 |
| `judge` / `judge_model` / `temperature` | 判定后端(本地/API/规则)、模型标签、采样温度 | 0.1 / 0.4 / 0.2 三个温度分别对应判定 / 反思 / 路由 |
| `seed` | 这次固定没固定采样种子 | **`null` = 没固定(默认行为)**,这时 ③ 不成立;有值时也只保证同机同版本大概率逐字一致,跨机仍不保证。取自客户端自己声明的值,不是环境变量猜的。**小镇实时面的一条更正(2026-10-06)**:此前这一项**恒为 `null`**,而每个请求体其实都带着种子 —— 因为起面路径既不给桥注入判定客户端、桥也没把挂在角色上的 provider 交给清单,于是"②能不能被核对"断了;现在客户端在**真发出去那一刻**把值声明回实例、桥把两类客户端一并上报(`case01/tests/test_mavis_provider_safety.py` 钉住)。同日三条真跑的 `manifest.seed` 仍是 `null`(那次跑在改码之前),要引"记录里看得见种子"须重跑一条。 |
| `manifest_warnings` | 这次跑缺了什么 | **只透出、不改判定**;`absent`=老记录没清单,`error`=清单自身生成失败 |

本地算哈希(在**项目根** `provenance/provenance` 下跑,不是 git 根;需要
`pip install -e packages/mavis-case01-injector`):
```
python -X utf8 -c "from mavis_case01_injector.manifest import file_sha256, dir_content_sha256;
print(file_sha256('cases/case01_stock/scenario.yaml')); print(dir_content_sha256('case01/data/financial'))"
```

**怎么数**(别照抄本节数字,它只反映写下那一刻;在**项目根**跑):
```
python -X utf8 -c "import json,glob,os; ds=[d for d in glob.glob('case01/runs/*') if os.path.isdir(d)];
r=[json.load(open(os.path.join(d,'run.json'),encoding='utf-8')) for d in ds if os.path.exists(os.path.join(d,'run.json'))];
m=[x.get('manifest') or {} for x in r];
print('记录',len(r),'带清单',sum(1 for k in m if k),'带 seed 键',sum(1 for k in m if 'seed' in k),
'其中有值',sum(1 for k in m if k.get('seed') is not None))"
```

**哈希对不上时先查行尾**:`file_sha256` 会先把 `\r\n`/`\r` 归一成 `\n` 再哈希,
所以它对 LF 文件与 `sha256sum` 同值(本机实测 `scenario.yaml` 两边都是
`a98e1748…6c6f54`),但 Windows `core.autocrlf` 检出的 CRLF 副本直接 `sha256sum` 会不一样。
这不是内容变了,请统一用上面那条命令比对。

**边界(不粉饰)**:`manifest` 是分三步落地的——注入器路径 2026-09-22、生产路径 2026-10-04、

## 五、③ 能做到什么程度,还差什么

- **seed 是可选开关,默认不设**(2026-10-04 起)。设了才透传:本地 Ollama 的
  `/api/chat` 走 `options.seed`、`/v1/chat/completions` 与 vLLM 走顶层 `seed`
  (`packages/mavis-case01-injector/src/mavis_case01_injector/llm.py`),用的值由 `manifest.seed` 记下。
  入口:`case01 run --seed`、`batch_run --seed`(整批同一个值)、`batch_run --seed-base N`(逐条
  `N+i`,序号取自 run_id 末尾 ⇒ 重试沿用同一个值;每条的种子记在**自己那行台账的 `seed` 栏**,
  因为 `cmd` 字段里永远不会有种子——它走 env),`CASE01_LLM_SEED`。
  小镇面(5010)的入口:`live_switch.py --start case01 --seed N --run-id X`,或一条命令起全部面
  `python tools/serve_all.py --full --seed N --run-id X`(2026-10-06 补的透传——此前这条 README
  推荐的入口会把 `--seed`/`--run-id`/`--nodes` 静默扔掉,现在少了 `--full` 就在起跑前拒)。
  后两者互斥,起跑前就拒,不会烧掉半批才发现设定写错。
  **不设时请求体与加这段代码之前逐字节同**,温度仍是 0.1 / 0.4 / 0.2 而不是 0,
  所以默认产物依旧不可逐字重生成。生效范围(2026-10-06 起已扩大,原文那句"桥内 provider 不受约束"已过期):
  除我们自己的客户端(T0 回答、反思、路由、两个判官)外,**mavis 桥里的角色台词也带 `seed`**——
  桥把每个 agent 的 `_llm` 换成 `case01.agents.mavis_provider.Case01SafeProvider`,该类的请求体现在补 `seed`
  (由 `case01/tests/test_mavis_provider_safety.py` 三条测试钉住"发出去的字节",不联网);
  并且**世界动力学那条进程全局 RNG 也会被播种**(`case01/rngchain.py`:按 `sha256(scheme|world|run_id|master)` 派生)。
  ⇒ **对外仍然只有一个数**:派生值只落在记录旁的 `rng.json`,不进 manifest 键集。
  ⚠ **这句要限定清楚,否则会被读成"敲这一个数就能重跑出同一条"**:那个数固定的是
  **采样参数 + 两条流的派生规则**,而世界流的**取值**是 `sha256(scheme|world|run_id|master)`
  —— 里面**含 `run_id`**。所以**要重跑"同一条"必须同时给 `--seed` 和 `--run-id`**;
  只给 seed 而让 run_id 现铸(批样本每条都现铸、小镇面每次"重开一局"也现铸)拿到的是
  **同一种子下的另一条世界流**,不是原来那条。
  ⚠ **但这条"换名字就换世界流"只在跑得动引擎的路径上才有意义**(即 5010 小镇面):
  批/单条路径根本不从这条流取数(见下面"想要多样本就得换 master"那条)。
  **重开一局本来就该有新名字**,所以这不是缺陷;要说清的是**②/③ 的对照只在
  seed+run_id 这一对都固定时才成立**,而当时用的到底是哪条世界流,当场看
  `rng.json.world_seed` 就有(它同时记 `master`/`model_seed`/`rng_scheme`/`run_id`)。
- **⚠ 想要多样本就得换 master,不是多跑几条(2026-10-06 实测)**:批/单条路径上
  **没有世界流的消费者**——全仓唯一的 `random.*` 调用就是 `case01/rngchain.py:174`
  那句 `random.seed(world)`,15 个取数点全在 `mavisframework`(`agent_core.py:307 random.choice(tiles)`
  这类),而只有小镇/引擎路径会跑到它。⇒ 同一个 master 在**同一服务端状态**下多跑几条,
  拿到的是**同一份内容**:12 条同 master、单 lane 实测**内容只有 2 种**(空载那 1 条一桶,
  暖的 11 条反思 sha `8b938ad0fb` 逐字节全等,`world_seed` 却条条不同)。
  所以"③ 桶内全等"和"样本多样性"是同一件事的两面:**全等发生在状态桶内,多样性只能来自换 master**
  (`batch_run --seed-base N`,逐条 `N+i`)。拿并发形态去造多样性(3 lane 同 master 实测能拆出 28 种)
  虽然也"不同",但那把"这条为什么不同"从种子换成了调度,**不利于归因**。
- **模型身份只记标签**:`judge_model` 是 `qwen3:8b` 这种 tag,**而且是客户端声明值**——服务端实际换成了别的模型
  它看不见。服务端侧的实测(版本、驻留模型)与解释器/引擎版本、当时的 git 提交与工作树脏数,
  一起落在 **`rng.json.environment`**(2026-10-06 起;**只在传了 `--seed` 时才探**,默认路径零新增开销)。
- **推理平台不进 manifest**:Ollama/llama.cpp 版本、GPU 后端与量化实现都会带来漂移;跨机逐字一致**不承诺**。
- 把温度设成 0 是最省事的贪心路线,但那**改的是判定行为本身**,与"忠实于源设定"冲突;
  若要做,只能作为演示配置单列,不能当研究配置。

§五 说的最小加法**只做了一半**:请求体透传 `seed` + `manifest.seed` 留痕已落地(2026-10-04,
默认不启用、不改任何现有行为);2026-10-06 补上了桥内 provider 的 `seed`、引擎 RNG 的播种与环境身份留痕。
**还缺的是**模型权重摘要。**所以对外口径的边界从"能不能"挪到了"什么条件下":**

> ③ 可以写进评审材料,但**只能写成有条件**:"同机、同一模型驻留、同一预热形态下重跑逐字一致(已实测),
> **跨机/跨版本/跨状态不承诺**"。把 `manifest.seed` 有值直接读成"任何人都能逐字重跑出同样的回答",**仍然是越界**。

### 五·补 实测:固定 seed 下输出有**两个**稳定值(冷/热双稳态)

2026-10-05 用 `Ollama 0.35.0` + `qwen3:8b` 做受控实验,发现一个比"跨机漂移"更近的坑:
**同一台机器、同一 seed、同一 prompt,输出会分成两个各自完全稳定的值,取决于模型当时是否刚被载入。**

| 条件 | sha256(前 10) | 正文长度 | 单次耗时 |
| --- | --- | --- | --- |
| **冷加载后首次**推理 | `1fe3ff84c7` | 438 字 | ~11 s |
| 之后**热态**推理 | `b7996f80b1` | 388 字 | ~3.6 s |

复现方式(每次先 `POST /api/generate {"keep_alive":0}` 卸载,再跑):

- 连续 4 次"卸载 → 冷起":**4/4 都是** `1fe3ff84c7`;
- 卸载后同进程连跑 3 次:**第 1 次** `1fe3ff84c7`、**第 2/3 次** `b7996f80b1`;
- 3 路并发(模型已热):**3/3 都是** `b7996f80b1`。

**这推翻了一个更直觉的猜测**:差异不是并发造成的 —— 并发批反而**全一致**,而串行批里
第 1 次与第 2、3 次不同。真正的变量只有一个:**这一轮推理时模型在显存里是冷的还是热的。**

为什么值得写进口径:

1. **它解释了历史数据的"假随机"**。批次 `batch-261004-220441-h120seed`(35 条,同 seed
   `20261004`、同模型 `qwen3:8b`、同场景、`temperature` 与 `prompt_versions` 全部唯一)产出
   **16 个不同的 T0**。按台账 `ts` 还原时间线后可见:它是**6 轮 × 3 路**的节奏,同一路在相邻
   轮次反复落到同一个值 —— 这正是"每轮只有一条撞上冷起、其余走热态"的形态,不是采样发散。
2. **它给"逐字复现"加了一条更硬的前提**:**跑法必须一致**。要么每条之前都卸载(全冷),
   要么先预热再连跑(全热)。混着跑,即使 seed 相同也会得到两个值。
3. **它不改变对外结论**。冷/热都在同一台机器上,跨机仍会另有漂移;而且 `manifest` 目前
   **没有**任何字段能记录冷/热,所以逐字复现的门槛没有降低。

测试侧已把它钉成契约:`case01/tests/test_reproducibility.py::test_seed_does_not_appear_to_guarantee_verbatim_across_model_reloads`
(断言 manifest 里不得出现冷/热相关字段;若将来加了,该测试会红,提醒同步修订本节)。

**4) embed:驻留快照当不了判据(那半截是负面结果);换成"同一 query 打两次"之后测完了**

原假设是"跨桶时 `retrievals` 换一半,可能是 embedding 模型的驻留状态"。为此跑了一轮专门设计
(1-token 每 55 秒把 chat 钉在显存里共 9 分钟、期间完全不碰 embed,再连跑三条同种子)。**结果 A ≠ B = C**
(B/C 与串行暖桶基准逐字节全等),A 只能说明"存在第三种服务端形态",归因未定。

⚠ **本节初稿写过"`/api/ps` 看不见 embedding 模型",那句是错的,已订正**:13:09:07 实测抓到过
`qwen3-embedding:0.6b-q8_0` 在驻留列表里,而随后 6 次连续 12 秒间隔采样都没有它 ⇒ **它只在被调用的
那几秒出现,卸得很快**。真正的问题是**两个探针几乎总取在它不在场的时刻**:
`rng.json.environment.ollama_resident` 的探针跑在 run 开头(播种那一刻,embed 还没被调),
而批处理台账里那个 `_ollama_loaded_model()` 探针**按能力字段刻意筛掉了 embedding**。
"几乎"不是"永远"——当日 13:47 复算全库:批路径 `--seed-base` 那 20 条里,**`-016` 一条的
`rng.json` 同时记到了 `qwen3-embedding:0.6b-q8_0` 与 chat 模型(1/20)**,其余 19 条只有 chat
⇒ 驻留快照**能**抓到 embed,但抓到是偶发,**不能当判据**(抓不到也不代表那局没调 embed)。
⇒ 想判"检索本身确不确定",不该看驻留,而应**拿同一个 query 打两次(含跨进程)比 hits/score**
(链路:`case01/agents/financial.py:_vec` → `llm.embed`)。

**已按这条判据测完(2026-10-07 下午,三个独立进程;脚本 `_retrieval_determinism_261007.py`、

**5) 小镇面(5010):把 id 与桶一起钉死,仍然不等 —— ③ 在这一面确实不可达**

第一次补测(`261007-e5-a` 两局)是**冷 vs 暖**,不算:第 1 局 `resident=[4b]`,64 分钟后补跑那局
`resident=[]`(越过 `keep_alive`)。第二次(`261007-e5c-a`,先验证驻留再连跑两局、同 `--seed` 同 `--run-id`)
两局 `rng.json` 实测 `ollama_resident` 都是 4b、`world_seed` 都是 `9834390279068484169` ⇒ **所有已知变量都钉死了**,
而 `raw.json` 依然不等(`4e5a6604f567` vs `e31c769c2ef4`)。残差定位到字段级:

| 两局**逐字相同** | 两局**不同** |
| --- | --- |
| `world_audit`(事实推进)、`branch`/`branch_source`/`branch_mode`、`condition_monitor`、`c_plan`、`roles`、`scenario_dir`、`finish_reason`、节点数与每节点的 `node_id`/`events`/`date`/`context`/`interaction_started` | `nodes[].agents`(角色行为与位置)、`nodes[].dialogue`(台词文本)、`judge_info`(判词措辞)、`elapsed_s`、`summary`、`manifest*` |

⇒ 这比 §五·补三 强一档:那次的 A vs B 没有同时钉住 `run_id` 与桶,而**这次钉死之后仍然不等**,
所以"小镇面只到 ②"不是"条件没给够",而是**这一面的残余不确定在引擎/桥侧**
(§五·补三 机制条②:`prompt/scratch.py` 在组装提示词时就消耗全局 RNG,上游一不同后面就不同)。
⇒ **演示日若要做逐字对照,只能走批/单条路径**;小镇面对照的是上表左列那一组字段,不是 sha256。
⇒ 新增细节:小镇面的**总轮数也不保证**(另两局实测 7 vs 5)。

⚠ **方法论(今天我自己连踩两次)**:判"某一局跑完了"**不能用"产物文件存在"**——复用旧 `--run-id` 时
上一局的文件还在原地,轮询会秒过,于是紧接着的 `--stop` 把自己刚起的那局杀在 20 秒处
(实测 `raw.json` 的 mtime 停在上一局的时刻,而日志写着"有")。要用 **mtime 晚于起跑时刻**当判据,
或先把旧目录挪开;并顺手核对 `rng.json` 的驻留字段,确认自己比的确实是同一个桶。
