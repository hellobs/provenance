### 方案 B(现场真跑一局,需 Ollama)

```powershell
cd D:\zzr\provenance\provenance
.venv-live\Scripts\python.exe live_switch.py --start case01 `
  --seed 20261015 --run-id demo1015-live --hold 1800
```

- ⚠ **`--seed` 与 `--run-id` 两个都要写,少任何一个这句话就白答**:下一行问答要说
  "seed 设了",而此前这条命令里**一个都没带**(照它跑就是非确定路径,当场被追问会很难看)。
  `--seed` 固定采样参数与两条流的**派生规则**;而世界流的**取值**里含 `run_id`
  (`sha256(scheme|world|run_id|master)`)⇒ **不给 `--run-id` 就每次现铸名字,拿到的是同一种子下的
  另一条世界流**,不是原来那条。名字同时也是深链 `?run=demo1015-live` 与彩排对照的键。
  派生参数与环境身份落在记录旁的 `rng.json`(成品记录与原始记录旁现在各一份)。
- ⚠ **`--nodes N` 现在是真生效了**(2026-10-06 前它在默认 judge 模式下会被换回完整序列,
  实测按 4 跑出 7 个节点)。要收进时间窗可以加 `--nodes 3`,但**加完耗时口径要重测**——
  紧接着的耗时口径(2–6 分钟)是**全节点**实测;旧版那句"一局约 2 分钟"写于节点未被真截断的旧行为,已订正。
- ⚠ **预热要按 `num_ctx` 预热,不是随便发一个请求**(2026-10-07 实测两次):
  ```powershell
  curl.exe -s http://127.0.0.1:11434/api/generate -d "{\"model\":\"qwen3:8b\",\"prompt\":\"hi\",\"options\":{\"num_ctx\":32768},\"max_tokens\":1}"
  curl.exe -s http://127.0.0.1:11434/api/ps   # 确认它就在那儿,再开正式那条
  ```
  只发 1-token 而**不带 `num_ctx`** 的预热,是把模型按默认小上下文加载;正式那条一上来要把它
  升到 32768(反思/路由的长 prompt 需要),这一升就是 **~185 s**(同日实测对照:带 `num_ctx` 预热只要 **16 s**),
  而 185 s 会**顶穿单发请求 120 s 的超时**(当时 `OllamaClient chat failed after 3 retries: timed out`,
  E8 整批与 E9 的 8b 首条就是这么死的)。现在客户端默认已给到 300 s,但**预热仍按上面这条做**——
  余量是兜底,不是替代配方。
- ⚠ **预热后的第一条只当垫子,别当正式那条**(2026-10-07 E9 两臂实测):同种子、同驻留、单通道下,
  **两臂的批次第一条都是各自臂里唯一与规范输出不同的一条**(4b 那条探针时刻 embedding 与 chat 同驻,
  连检索命中都换了一批;8b 那条多经历一次上下文重分配)。取**第二条及以后**,才与彩排基线对得上。
- ⚠ **本机 8GB 显存上 qwen3:8b 串行推理,单条 2–6 分钟**(实测全流程约 6 分钟,首轮 T0 更久;与本文第五节口径一致,别再说"约 2 分钟");
  ⚠ 但 2–6 分钟**不是上界**:预热不当或首条垫子出现过 **1035 s**(含一次超时重试)、**895 s**(4b)。排时段按最坏留。
- 现场务必**提前跑完**,演示时只翻记录,别让评委干等。
- 更细的播种与彩排步骤在 `D:\zzr\GTC\docs\261006_现场单条run最大化可复现_演示日runbook.md`
  (那份的参数与本条一致:`--nodes 3 --hold 1800 --run-id demo1015-live --seed 20261015`)。
- 想一条命令连只读面一起起(README 推的那个入口),同一对参数走 —— 在 `D:\zzr\provenance` 下:
  ```powershell
  provenance\.venv-live\Scripts\python.exe tools\serve_all.py --full --seed 20261015 --run-id demo1015-live
  ```
  它自己探测解释器(演示机上落到的还是同一个 `.venv-live`),起的是 5010 真跑 + 5002/5003/5020。
  **没带 `--full` 时这条入口会拒掉 `--seed`**(起一个"以为播了种、其实只翻记录"的面,
  比不如有一个明确报错)。

## 五、故障回退(现场会踩,先背下来)

| 症状 | 原因 | 处置 |
|---|---|---|
| 打开记录详情**白屏** | 脚本把 `source` 猜成了 `checkpoint`/`compressed` | case01 记录一律用 `source=review`;`checkpoint`/`compressed` 只服务 case00,**对 case01 本就 404** |
| 调 API **404** | 用了 query string | `run-detail` 是**路径参数**:`/api/run-detail/{source}/{run_id}`,不是 `?id=` |
| 调 API **404**(第二种,2026-10-09 实测) | 在 **5010** 上调了 `/api/runs/{run_id}` —— 这条路由**只在 5002 有**(`case01/serve.py:149`) | 5010 的详情面是 `/api/run-detail/{source}/{run_id}`;别把两个端口的路由表混着用(逐面清单见《平台对接契约_5010唯一入口》§3.4) |
| `/api/runs` 里找不到某条 | 它是 `questionable`(被默认排除) | 加 `?include_questionable=1`;或看 `excluded`(5010 是 `excluded.runs` 列表) |
| 平台侧说"这条建不出单" | `GET /api/review-package/{run_id}` 回 **HTTP 200 但 `data.status=blocked`**、`task_candidates` 为空 —— 不是接口坏了。实测四条:`auto`/`B` = `ready`(10/8 个候选),`A`/`C` = `blocked`,原因码 `run_not_reviewable` | 这是质检门在建单入口的同一道拦截(`quality` ∈ questionable/debug/deprecated/unreadable 就 blocked)。话术:"**入口拒绝给不合格记录建单,并且把拒绝理由如实回给平台,不是静默给空表**";要演建单链路就用 `demo1015-auto` |
| 界面打不开 | 5010 没起来 / 被别的 case 占 | `cd D:\zzr\provenance\provenance` 后 `.venv-live\Scripts\python.exe live_switch.py --start case01 --review-only` 重启 |
