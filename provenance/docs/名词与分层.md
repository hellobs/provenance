# 名词、分层与数据流（谁是谁、谁在哪层）

> **状态**:现行
> **最后核对**:2026-09-22
> **说明**:**名词、分层与数据流**:五个名词各是什么/在哪层 + 引擎的 case01 味道审计 + 搬 ①② 不搬 ③ 的决定
> "引擎带 case01 味道"的审计结论与随之而来的决定(搬 ①②、不搬 ③)。**下一个人最容易搞混的就是这页。**

## 一、五个名词各是什么、住在哪

| 名词 | 住在哪 | 是什么（一句话） | 不做什么 |
|---|---|---|---|
| **mavisframework**（"mavis"） | `mavis/`（独立仓，tag v1.2.1） | **小镇内核**：agent 的记忆流/检索/反思/日程/行动 + 步进循环 + 瓦片与碰撞 + 提示词 + 配置加载校验 + 插件面。斯坦福 Generative Agents 那一套的中文化 + IVD 改造 | 不含任何案例词、不做编排、不做可视化 |
| **case_engine**（"引擎"） | `provenance/provenance/case_engine/`（2342 行） | **实验协议执行器**：把一局研究写成声明（scenario）→ 切节点 → 判分支 → 查一致性 → 要反思 → 切成人能审的问题 → 落盘 → 只读交出 | 不模拟人（那是 mavis）、不画画面（那是 vizkit）、不做专家工作台（那是 live/平台）、不决定走哪条线（由 agent 的回答决定） |
| **mavis-vizkit** | `provenance/packages/mavis-vizkit/` | **mavis 的可视化插件**：把一局画成小镇（Phaser/贴图/气泡/右栏卡片）。这才是 mavis 意义上的 **extension** | 不产生行为、不认识案例 |
| **case00** | `provenance/provenance/case00/` + `cases/case00_village/` | **案例**：6 角色投资咨询中心（原初场景，已冻结）；数据 = agents/maze/relationships/story/governance | 它的"跑一局"由**案例宿主**（`live_fastapi.py` live 面 + mavis）负责，不由引擎跑 |
| **case01** | `provenance/provenance/case01/` + `cases/case01_stock/` | **案例**：2 角色（Ethan Lin + Investment AI）节点驱动推演；含注入器、只读契约、结果面板 | —— |

### 分层图（依赖单向向上）

```
⑤ 平台/嵌入面   5010 实时面 · 5002 case01 只读契约 · 5004 多场景只读 · 5020 布景
                      ↑ 只读消费
④ 实验编排      case_engine —— scenario(数据) + 引擎策略(机制)   ← 「引擎」在这一层
                      ↑ 只调 Simulator(register_condition / simulate)
③ 案例(数据+事实) case00_village / case01_stock / case02_minimal
                      ↑ 用 mavis 的配置资产与插件面
② 小镇内核      mavisframework —— 记忆/检索/反思/日程/瓦片/步进循环  ← 斯坦福那一套在这
                      ↑ 被呈现
① 可视化插件    mavis-vizkit（挂在 mavis 插件面上的 extension）
```

## 二、case_engine 到底在做什么（六件事）

1. **写成声明**：`config.py` 定义一份 scenario（roles / state_schema / timeline / branch / consistency / reflection / router / retrieval / value_tendency / assets / params / meta.engine），加载、校验、给默认值；`scenarios.py` 从 `cases/` 自动发现。**场景是数据，加案例不改引擎。**
2. **切成节点**：`nodes.py` 由时间线**确定性**生成节点序列（日期 / 当日释放事件 / 必要交互 / 世界事实），默认首尾节点必须发生交互。
3. **判定走哪条线**：`branch.py` —— `LLMBranchJudge`（把 AI 自己的 T0 回答喂进判定器）或 `RuleBranchRouter`（无 LLM 词表降级）；`consistency.py` 比较 T0 立场与实际分支是否自相矛盾（**只检查留痕，不丢弃重跑**）。
4. **反思 + 切成可审问题**：`reflection.py` 生成反思正文（含 boilerplate 清洗）并解析成 router issues（检查项 + 风险等级 + 风险说明）；`retrieval.py` 给这一局**找资料**（文档向量检索，不是 agent 的记忆检索）。
5. **装引擎**：`engines.py` 注册表 + 工厂（`register(id, builder)` / `build_for(scenario)` / `supported_by` / `describe`）；`strategy.py` 策略接口只有 `supports/describe/panels/run`；`conditions.py`（14 行）用 `@Simulator.register_condition` 往 mavis 注册条件类型 —— **与内核的唯一接触点之一**。
6. **交出去**：`cli.py`（`list / show / run --engine / engines`）+ `serve.py`（5004 只读：`/api/scenarios`、`/api/scenarios/{id}`、`/api/engine-components`）。

**两个引擎策略的实际差别**：

| 引擎 | 它真做什么 | 碰 mavis 吗 |
|---|---|---|
| `experiment-eval`（case01_stock / case02_minimal） | **免 LLM 的确定性真跑**：场景数据 + 一条给定回答 → 分支/状态/一致性，落盘 `<case>_exp.json` | **不碰** |
| `sandbox-value`（case00_village） | **装配预检**：核验声明能否指向 mavis 可装配的资产/参数/价值权重，逐项 `ok/detail`；**不假装跑完整模拟** | 只通过 `register_condition` / `simulate` 间接 |

## 三、"治理"在这个项目里有两个意思（最常混的点）

| | 含义 | 在哪 |
|---|---|---|
| **A. agent 侧治理（内化）** | 专家设定的期望目标权重 → 约束角色行为 → 后果反馈 → **倾向演化** | **mavis**：`runtime/governance.py`、`runtime/consequence.py`、`agent_core.attach_governance()`；这是 IVD 的内化点 |
| **B. 平台侧治理（外部工作台）** | 专家审核反思、拆问题、干预、建单归池 | **provenance/平台**：live 面板（`/embed/goals`、干预时间轴）、`case01/review_app`、5010 契约、平台侧流程 |

**专家看到的数据是一条链**：反思原文与倾向演化来自 **A（mavis）** → 组织成"待审问题"由 **case01** 负责 → 让整局可声明/可复现/可换引擎由 **case_engine** 负责 → 摆给专家并接受干预由 **live/平台** 负责。
**case_engine 既不生产治理机制，也不做干预**（它连 `governance.json` 都不写）。

## 四、审计结论：引擎确实带 case01 味道，而且只有 case01 在真用

2026-09-21 审计（全仓搜引擎各入口函数的消费者，排除引擎自身与测试）：

```
value_tendency_args / reflection_args / branch_args / consistency_signals
eval_inputs / select_timeline / merge_t0 / build_for / supported_by      → 无人引用
nodes_from_timeline                                                      → 只被 case01/injector 引用
```

加上 case00 的 live 链路对 case_engine 的引用只有 `engines.components(eid)`（面板开关表）与
`config.load_yaml()`（读引擎 id）—— 结论：

> **引擎现在是一台"受控实验协议机"，case01 是唯一在跑它的案例；case00 只是被它登记与预检。**
> 这不是设计失误，是**抽取顺序**造成的：case_engine 是 2026-09-20 从 `case01/injector`（6,447 行）
> 剥出来的，抽象时用的是 case01 的实验形状（T0 触发 → 一个可判定结论 → 分支线 → 一致性 → 反思切问题）。
> 凡符合这个形状的案例都能直接用（**case02_minimal 零引擎改动就跑起来了**，通用性已被证明），
> 不符合的（case00 这种长期演化 + 专家干预）就只落到"登记 + 预检"。

## 五、由此产生的决定：搬 ①②，不搬 ③

"权重那一套"其实散在三处，必须分清哪部分该进引擎：

| 成分 | 归属 | 决定 |
|---|---|---|
| **① 权重声明**（governance + initial_tendency 两本账） | `cases/case00_village/scenario.yaml` 的 `world.value_tendency` | **进引擎**：声明是唯一来源 |
| **② 权重装配与映射**（声明 → `governance.json` / 各角色初始倾向） | 新增 `case_engine/config.value_tendency_plan()` | **进引擎**（本次已落地） |
| **③ 权重机制**（约束如何进决策、后果如何改倾向） | mavis：`governance.py` / `consequence.py` / `attach_governance()` | **绝不搬**：这是 IVD 的内化点，动了就破了"记忆与倾向归内核"这条不变量 |

**本次（2026-09-21）落地的是 ①②**：

- `value_tendency_plan(cfg)`：把声明解析成"能不能落到每个角色"的映射计划 + 逐项体检
  （缺账 / 维度为空 / 取值非数值 / 和不为一 / 声明里多出的角色键），并给出 `materialize`
  ——"若据声明生成资产，应该写成什么"；
- `SandboxValue.run()` 的预检**改用这份计划**（原先只查"这个名字在两本账里出现过没有"，
  看不出缺一整本账、维度为空、多了别人的键）；
- 新增 `case_engine/tests/test_value_tendency_single_source.py`：**资产必须等于声明**
  （逐角色逐维度比对 `governance.json` 与各 `agent.json` 的 `initial_tendency`，1e-9 容差），
  谁只改一边 CI 就红。**这就是"单一来源"的可执行含义**；
- 现状实测：case00 的资产与声明**当前完全一致**（无漂移），四条守卫全绿。
**落盘器(② 的"执行"一半)**:`case_engine/value_tendency.py`

- `materialize(cfg, base, apply=False)`:把 `plan.materialize` 写进 `governance.json` 与各
  `agent.json` 的 `initial_tendency`。三条硬规矩:**声明为准**(单向覆盖资产)、
  **默认不写**(`apply=False` 只 dry-run 并逐项报告)、**不动排版**(按原文件缩进宽度与末尾换行写回,
  否则每次落盘都是巨大 diff)。缺声明 / 某角色缺账 → **拒绝落盘**;声明里多出的角色键 → 报出来
  但合法部分照常落盘(`ok=False` 表部分完成)。
- CLI:`python -m case_engine materialize-value-tendency <case_id> [--apply] [--base …]`
  (默认 dry-run;退出码 3 = 有问题)。
- 配置工具(mavis 仓 `config_tool`)不再自己写一份口径:新增
  `scenario_builder.governance_payload(scenario)`,**优先调用引擎的映射**,引擎不可用时退回本地口径
  并在返回值里标 `used_engine=False`(不静默换口径);`app.py` 保存场景时改调它。

**测试(共 17 条守卫,全绿)**

- `case_engine/tests/test_value_tendency_single_source.py`(4):声明自洽 / **资产==声明** /
  预检确实用上计划 / 声明被改坏时必须如实报 unknown+missing;
- `case_engine/tests/test_value_tendency_materialize.py`(11):dry-run 不动文件 /
  apply 写对值 / **幂等** / 漂移被声明覆盖 / **排版保持**(该测试当场抓出"先截断后读原文件"的真 bug
  —— 写盘前必须先把文本算好)/ 缺声明与缺账**拒绝落盘** / 多余角色键只报不拦合法部分 /
  CLI dry-run→apply→一致 / **真实 case00 上 apply 后哈希不变**;
- 外层 `tests/test_config_tool_value_tendency.py`(2,跨仓):config_tool 生成的 payload
  **逐字等于**引擎映射结果,且等于仓里真实的 `governance.json`。

**唯一仍未收口**:`config_tool` 位于 mavis 仓却依赖 case_engine(依赖方向仍反),
本次只让它**复用**引擎函数、没有搬家;等决定搬家时一起处理。

## 六、还没做（等你定）

- **路线 B（对称化）**：新增 `sandbox-live` 策略，把"起 mavis 跑 N 步 + 落 checkpoint + 产出记录"
  从 case00 的 live 面搬进引擎 → 两台引擎都能真跑，且可**脱离实时面批量跑**（参数扫描 / CI 冒烟）。
  代价：5010 是当前唯一实时宿主（画面/WebSocket/面板都挂它），要设计清"谁持有 Game/Simulator、
  谁写 checkpoint、面板怎么读"；顺带说，已定的"沙盒不允许回滚"让这件事更简单（批跑本就不接受在线干预）。
- **路线 C（协议显式化）**：在声明里加 `protocol: experiment | sandbox`，词表随之分家
  （experiment 用 branch/consistency/T0；sandbox 用 tendency/governance/timeline/intervention）。
  这样"case01 味道"从默认值变成**可选协议之一**，第三类案例（谈判、运营、多阶段对抗）来时是
  "加协议"而不是"往实验形状里塞"。
- **引擎角色如实标注**：`engines.describe()` 增加 `role: runner | precheck`，前端「引擎」页照实显示
  "这台能跑 / 这台只预检"，消除"两台看着一样、其实一台不会跑"的误导。
- **sandbox 走专家审核链(只审 AI 助手,已定 2026-09-22,已实现)**：case00 六角色仅 `ai_advisor`
  是 `ai_tool`,其余五角色都是 `user`(咨询方/分析师/风控),不产生"AI 自主判断"可审。
  专家审核链语义 = 审 AI 形成的观点(反思+切问题),故 case00 若要进审核链,
  **只监控 `ai_advisor`**,与 case01 审 `investment_ai`(唯一 ai_tool)同构,非新造机制。
  **实现(2026-09-22)**：在 `SandboxValue.run()` 加可选阶段——调用方经 `kw` 传
  `evolution={agent, checkpoints, interventions, tendency_keys} + llm`,且目标是 ai_tool
  角色即触发:`assemble_evolution_material`(从 checkpoint 倾向轨迹+干预组装经历自述)
  → `run_reflection`(新增 `material` 注入参数) → `run_router`(issues 分流,进平台审)。
  返回追加 `audited_agent/reflection/router` 段;`run_type` 仍 `assembly-check`。不传
  evolution/llm 则保持纯预检,绝不假装产反思。case00 场景 `meta` 声明 `protocol: sandbox`
  + `audit_target: ai_advisor` 标注事实;审谁由调用方传,场景不锁死。**不改引擎**
  (消费调用方数据 + 复用现有 reflection/router)。与治理面板"即时纠偏"叠加同一主体,自洽。
- **`config_tool` 归属**：它在 mavis 仓却深度依赖 case_engine（55 处反向引用），
  是唯一一处依赖方向反了的地方；本次的 `value_tendency_plan()` 正是它应当复用的函数。
