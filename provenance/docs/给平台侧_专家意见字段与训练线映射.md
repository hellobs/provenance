## 0. 为什么要这一页

《专家审核流程补充规范》第 3 节把审核结论冻结为 `verdict ∈ approve / edit / reject`,
而本平台的标记端点 `POST /api/reflections/mark` 只认
`correct / incorrect / partial`(`live/reflections.py`)。
**本页发出时,两套词汇之间没有任何映射,也没有任何代码认 `approve`/`edit`(全仓检索 0 命中)。**

后果是:平台库里每多攒一份专家意见,本平台的训练集仍然是一条也进不来——
按现状提交会得到 `{"ok": false, "errors": ["verdict 必须是 correct/incorrect/partial 之一"]}`,
而导出侧 `case01/tools/lora_prep.py:93` 会把这类记录整条静默剔出训练集。
本页给的就是那条缺失的桥。规则本身不改,只补"同一份意见怎么两边读"。

## 一、枚举对应(建议按此实现入向映射)

| 平台 `verdict` | 本平台 `verdict` | 该结论必填的文本 | 进训练集时取哪份文本 |
| --- | --- | --- | --- |
| `approve` | `correct` | 理由(见 §二,允许留空) | **原始反思片段**(`output = 原反思`) |
| `edit` | `partial` | 修改片段 + 修改理由 | **经确认的最终片段**(见 §三,不是任一专家的 `expert_edit`) |
| `reject` | `incorrect` | 核心逻辑为何不成立(§3:99 已强制) | 只进 DPO 的 `rejected=原反思`;`chosen` 缺最终片段则该条**不进训练集** |

- 一个 `issue + 专业类别` 一条任务(§1.2),所以一次映射产出的是一条 mark 记录,
  不是一批;同任务多轮/多专家的意见在平台侧计票,**到本平台只落"该任务的有效最终结论"**。
- 跨专业结论差异只并列展示(§4:107),**不要**折叠成一个统一结论再发给我们。
- 无多数(`no_majority`)经人工裁决的结论(§4:125)可以进来,但必须带
  `formation=adjudicated` 标记,不能伪装成五人多数。

## 二、字段变更(标记记录从 8 个字段扩到这些)

| 字段 | 谁产生 | 约束 | 说明 |
| --- | --- | --- | --- |
| `agent` | 服务端 | 必须是本局真实角色 | 现有;非本局角色一律拒绝(现在探针 `agent="x"` 能原样入库) |
| `run_id` | 服务端 | 必填 | **新增**。case01 的成品记录标识(现在只在 `simulation` 字段里等于 run_id,名字对不上) |
| `issue_id` | 请求方 | 必填 | **新增**。仅 Run 内唯一(§1.2:43),所以必须与 `run_id` 成对出现 |
| `expert_category_id` | 请求方 | 必填 | **新增**。专业归属,用建单时的目录版本快照 |
| `verdict` | 请求方 | 三选一 | 现有 |
| `reason` | 请求方 | **选填** | **新增**。独立于 `correction`——`approve` 也能留一句为什么。留空合法 |
| `correction` | 请求方 | 仅 `partial/incorrect` 填 | 现有。语义收窄为"该任务定稿后的最终片段" |
| `anchor` | 请求方 | **构造偏好对必填** | **新增**。原文定位(§7:173「原文定位」)。**为什么不能留空:见 §三·补 ①**——没有定位信息,一段百字改文回填不进整篇反思,偏好对就不成立 |
| `version` / `supersedes` / `active` | 服务端 | 追加版本、保留旧版 | **新增**(§3:101)。计票只取 `active=true` 的最新版本 |
| `formation` | 请求方 | `consensus`/`majority`/`adjudicated` | **新增**(§7:174「形成方式」) |
| `origin` | 服务端 | `expert`(缺省)/`simulated`/`backfilled` | **新增**。这条意见**是谁产的**。导出侧 `origin != expert` 一律不进训练集,必要性见 §三·补 ② |
| `operator` | 服务端 | 常量 `expert` | 现有,**语义保持"这条来自人工审核"**,不当身份用 |
| `expert_ref` | **仅服务端** | 服务端自有会话/配置才可填;取不到写 `unattributed` | **新增**。见下面这条硬边界 |

⚠ **专家身份:内部可留痕,外部不可指定。**
请求体里出现的任何 `expert_id` / `expert_ref` **一律丢弃并记日志**,绝不写入记录
(《补充规范》§3:79「提交时由平台账号确定 `expert_id`,不能信任浏览器传入的任意专家 ID」,
§7:183「不能统一写常量 `expert`」)。
本平台的 5010 面无鉴权,所以今天能诚实给出的只有 `unattributed`;
真正的人-任务对应关系由平台库持有,我们只存 `(run_id, issue_id, expert_category_id)` 让两边能对上。

## 三、训练侧取哪一版文本(需要研究侧拍板的一条)

《补充规范》§5:132 写明「`approve/edit/reject` 是对反思核心的判断,**Edit 的文字仍需单独确认**」,
§6:158 给材料打了 `original / expert_edit / final_reviewed` 三个来源标签。

因此建议:

1. DPO 的 `chosen` **只取 `final_reviewed`**(经本轮确认人数的最终片段);
2. 未确认的个别专家改文 `expert_edit` **可以入库留痕,但不进训练集**;
3. `results/lora/*.jsonl` 的导出条件从"有 mark 就导"改为"该任务已定稿且有 `final_reviewed`"。

不按此收窄的话,训练对里会混进"某一位专家未经确认的改法"当标准答案——
这正是 §5:134「平台不得自动拼接、选择最长一版」要避免的事,只是它发生在下游。

## 三·补、两条实测出来的管线缺陷(2026-10-07,已改代码)

这两条不是推测——是拿 4 条真 case01 反思、让 4b 扮专家走了一遍 `反思+issue → mark →
build_lora_sample → lora_prep --export` 才露出来的(标记写在临时目录,生产文件未动)。

**① `chosen` 与 `rejected` 不同量纲,旧校验门 4/4 全放过。**

| 对 | chosen | rejected | 逐字相似度 |
| --- | --- | --- | --- |
| 1 | 111 字 | 3387 字 | 0.026 |
| 2 | 124 字 | 1591 字 | 0.065 |
| 3 | 163 字 | 2201 字 | 0.059 |
| 4 | 126 字 | 1784 字 | 0.071 |

成因:`build_lora_sample` 用 `rejected = 整篇反思`,而《补充规范》§7:173 里专家交的是
**edited_segment(一个片段)**。这种对子训出来的是"偏好短回答",不是"偏好专家判断";
而旧 `validate_dpo` 只查空值与 `chosen == rejected` 全等,所以四条一条都没拦。
**已改**:`validate_dpo` 增加长度比 `min/max < 0.5` 的判据,理由写进 `reject_reasons`
(`DPO:chosen/rejected 量纲不对等(片段 vs 全文,ratio=…)`),SFT 那条不受牵连。
根治要靠 `anchor`(§二):有定位就能把片段回填成完整反思,两侧才可比。
**在 anchor 到位之前,段级改文不会产生合法偏好对**——这是事实,不是保守措辞。

顺带纠一处**我们自己写反的口径**(2026-10-07 对 0904doc 05 §二 时发现的):面板原先在改文框
上提示"整篇重写才能生成偏好对",而《HCI 增量需求》§二原话是「Edit 时,**仅修改自己负责的
问题 / 反思片段,不直接重写整篇 Reflection**」。⇒ 专家给片段是**正确形态**,不是没写完。
现在面板与 `validate_dpo` 的文案都改成:片段暂时进不了偏好对,这件事由**导出侧**按 `anchor`
重建整篇来解决,不许回头要求专家改成整篇。平台侧做界面时请照同一句话,别把这条约束又翻回
去(它一旦被翻回去,专家的输入就变成了"重写别人的整篇反思",而那不是我们要采集的信号)。

**② 模拟出来的"专家意见"与真专家意见逐字节不可区分。**

同一批数据加上 `origin=simulated` 之前,导出结果是 `sft: 4, dpo: 4, rejected: 0`——
校验门看不出这是被评估的那个模型自己扮的专家。而《LoRA 预准备》§四 的自述边界
("不从成品反思造自模仿 SFT:那是在教模型模仿自己,零新信息")正是要挡这件事。
另有一条相关的观测:让 4b 扮专家,四次判定 **4/4 全是 `edit`**,一次 `approve`/`reject`
都没有 ⇒ 模拟数据即使进了训练集,verdict 分布也是退化的,凑不出 §4 那张表的结构。
**已改**:`new_mark` 落 `origin` 字段(缺省 `expert`,历史标记不回填),
`export()` 把 `origin != expert` 一律拒收并记原因。

**③ 顺带:序列长度会顶穿训练起点配置(改的是文档与产物读数,不是判据)。**

真实反思实测 **1591 / 1784 / 2201 / 3387 字**(min/…/max),而 SFT 样本的 `input`
就是"前缀 + 整篇反思",实测 1616–3412 字。Runbook 第 4 步给的是 `seq ≤ 1024` ⇒
一到位就得截断,而反思质量分析(`D:\zzr\GTC\docs\261007_同种子偏移程度_分层测量.md` §13.6)
显示扣分集中在**尾部几维**(经验迁移 / 假设与不确定性 / 结果与判断过程)——截断正好切掉信号。
**已改**:`export()` 的 `stats.char_len` 现在把 input/output 的 min/中位/max 写进产物,
`seq` 照着它定,不再靠猜。起点配置改为 `seq ≥ 2048`(见《LoRA 预准备》§三)。

## 四、归池 ≠ 批准训练(界面与数据都要分开)

§6:156 原话「归池不等于批准训练,更不自动触发训练」。所以每条记录需要**两个互不相干的状态**:

- 流程态:`ready` / `pooled` / `superseded`(材料包状态,由平台持有,我们只存引用);
- 训练态:`not_for_training` / `eligible` / `excluded(理由)`(选样决定,**需另有人显式做出并留痕**)。

现在这两个概念在本平台是混的:任何一条 mark 都会被 `--export` 全量收进训练文件。

## 五、回传格式(已经按这个实现了)

**入向端点是 `/api/expert/decision`,词表用平台词**(不是 `/api/reflections/mark`——
那个口保留给自己的词汇,实时面在用;两个口最后走的是同一道判定门
`live/reflections.mark_gate_errors`,所以不存在"从这个口进得来、从那个口进不来")。

```
POST /api/expert/decision
{
  "run_id": "batch-261007-…-003",
  "issue_id": "issue-3",
  "expert_category_id": "E4",
  "verdict": "edit",               // approve / edit / reject,服务端映射成 correct/partial/incorrect
  "text": "……专家写的文本……",      // edit/reject 必填;approve 给了会被拒(不静默丢)
  "reason": "披露层级到位,但未量化传闻证伪的回撤",   // 选填,不进训练集
  "anchor": {"sentence_ids": ["S012"], "quote": "…"}, // 取自交接包 task_candidates
  "formation": "majority"          // consensus / majority / adjudicated
}
```

- `agent` / `simulation(=run_id)` / `thought` / `sim_time` **由服务端从被审记录取**,
  请求体里出现 `agent`/`operator`/`origin`/`expert_id` 一律丢弃并记进
  `review.dropped_client_keys`(参照实测:一条都没写进记录)。
- §二 那张表里的新增字段落在标记记录的 **`review` 子对象**里,不摊平到顶层:
  训练侧只读顶层那几个字段,混进去会让"哪些字段进训练集"变成巧合。
  旧标记(2026-09-27 那 2 条探针)没有 `review` 键,读侧按缺键处理、不回填。
- 同一 `(run_id, issue_id, expert_category_id)` 再次提交是**追加一版**
  (`review.version` 递增、`supersedes` 指向前一版),旧意见不覆盖、不删除。
  计票与"哪一版有效"仍归平台(§7 的最小持久化里那条约束在平台侧生效)。

## 六、参照实现:怎么把它跑起来看

```powershell
# 5010 的 case01 面:只翻记录、不推演、不需要 GPU
python live_switch.py --start case01 --review-only     # 或直接用 .\serve.cmd
# 浏览器打开
http://127.0.0.1:5010/review/expert
```

**iframe 用哪个地址**:专家面板请用 `/review/expert`。`/embed/expert` 现在**只是它的别名、没有压缩版式**
(结果记录面 `/embed/review` 才有:前端按 `/embed/` 路径切 `body.embed`,见 `review_app.py:463`;
面板侧没接这套逻辑,已如实写在 `expert_review_app.py` 的路由清单里)。要我们把面板也做成紧凑嵌入版式,
说一声即可,那是前端样式改动,不动任何字段与接口。

四个接口各自要看到的东西:

| 接口 | 该看到什么 |
| --- | --- |
| `GET /api/expert/queue?limit=10` | 一条"问题＋专业"一行;`anchor.sentence_ids` 有值;`manual_triage`/`blocked` 计数不为零时**说明有样本 Router 没跑成**,不是"没问题";`review_state` 是任务级审核状态(05 §一要求的"当前审核状态",只给状态词不给上一份意见的内容),`pool` + `pool_generated_at` 是训练材料池状态(05 §六) |
| `GET /api/expert/read?run_id=…` | 反思全文 + 自然语言 Full Context;不含实验元信息(走交接包的专家安全视图) |
| `POST /api/expert/decision` | 返回里 `training_effect` 直接说这份意见进训练集会取哪份文本、SFT/DPO 校验门报了什么 |
| `GET /api/expert/marks` | **只有条数与专业分布**;结论和文本不在响应里(首轮两份意见互不可见) |

`training_effect` 这一项是特意做的:段级改文会被量纲门剔出偏好对(§三·补 ①),
面板当场讲出来,比导出时静默少一条有用。

⚠ 三个诚实边界,别当成已具备的能力:
1. 5010 面无鉴权 —— `marks` 不显示内容**不等于**内容受保护;
2. 面板不做分配(谁第一位、谁第二位)、不计票、不起争议轮,那些是平台的;
3. `reject` 的文本目前是"核心逻辑为何不成立",它会被 `build_lora_sample` 当作
   `incorrect` 的 `chosen` 用。**这与《补充规范》§5「rejected 不生成'已通过'的改写文本」
   不相容,属研究侧待拍**(拍之前该条只在审核材料里,别进训练集)。

## 八、本页不做的事

- 不替平台决定投票、争议追加三人、无多数裁决的界面(那是《补充规范》§3–§5 与 HCI 的事);
- 不声称本平台已有 `expert_id` 鉴权(§二中那条硬边界恰恰说明现在没有);
- 不改任何写接口的字段名——本页冻结后,本平台一侧的实现按 §二 单独提改动。
